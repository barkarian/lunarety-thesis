\begin{abstract}
	\addchaptertocentry{\abstractname} % Add the abstract to the table of contents
	
Η παρούσα διπλωματική εργασία πραγματεύεται τον σχεδιασμό και την υλοποίηση της πλατφόρμας «Lunarety», ενός προηγμένου συστήματος διαχείρισης τουριστικών καταλυμάτων (Property Management System -- PMS) που αξιοποιεί σύγχρονες τεχνολογίες για να προσφέρει λύσεις Rapid Development και ενσωμάτωση Τεχνητής Νοημοσύνης (LLMs). Σκοπός της εργασίας είναι η κάλυψη του κενού που υπάρχει στην αγορά για ένα εργαλείο που απευθύνεται σε διαχειριστές ακινήτων (Managers) οι οποίοι επιβλέπουν πολλαπλούς ιδιοκτήτες (Owners), προσφέροντας διαφάνεια, αυτοματισμό και ευκολία χρήσης που λείπει από τα παραδοσιακά Channel Managers.

Η μεθοδολογία ανάπτυξης βασίστηκε στη χρήση του PayloadCMS v3.0, το οποίο λειτουργεί ως ένα πλήρες backend framework εντός του Next.js, προσφέροντας Code-First ορισμό δομών δεδομένων και ισχυρή τυποποίηση μέσω TypeScript. Η βάση δεδομένων υλοποιήθηκε σε PostgreSQL με χρήση Drizzle ORM, εξασφαλίζοντας ακεραιότητα και ταχύτητα. Η πλατφόρμα ακολουθεί αρχιτεκτονική Monorepo και είναι σχεδιασμένη για Serverless Deployment (π.χ. Vercel), επιτρέποντας στους διαχειριστές να ξεκινούν με μηδενικό κόστος υποδομής και να κλιμακώνονται ανάλογα με τις ανάγκες τους.

Κεντρικό στοιχείο της καινοτομίας αποτελεί η ενσωμάτωση Large Language Models (LLMs) μέσω του Vercel AI SDK και του OpenRouter, προσφέροντας έξυπνες λειτουργίες σε πολλαπλά επίπεδα. Επιπλέον, αναπτύχθηκε ένας μηχανισμός «Auto Actions» για την πλήρη αυτοματοποίηση της επικοινωνίας μέσω πολλαπλών καναλιών (Email, OTA Messages, Telegram).

Η εργασία συνεισφέρει στην κατανόηση του τρόπου με τον οποίο οι σύγχρονες αρχιτεκτονικές λογισμικού και τα εργαλεία Rapid Development μπορούν να μετασχηματίσουν επιχειρησιακές διαδικασίες, προσφέροντας λύσεις υψηλής αξίας με μειωμένο χρόνο ανάπτυξης και συντήρησης.

\vspace{1cm}
\noindent\textbf{Λέξεις-κλειδιά:} Property Management System, Rapid Development, Large Language Models, PayloadCMS, Next.js, TypeScript, Serverless, Channel Manager, Auto Actions

This diploma thesis deals with the design and implementation of the «Lunarety» platform, an advanced Property Management System (PMS) that leverages modern technologies to offer Rapid Development solutions and Large Language Model (LLM) integration. The purpose of this work is to bridge the market gap for a tool tailored to Property Managers overseeing multiple Owners, offering transparency, automation, and ease of use often missing from traditional Channel Managers.

The development methodology was based on PayloadCMS v3.0, acting as a full backend framework within Next.js, offering Code-First data structure definitions and strong typing via TypeScript. The database was implemented in PostgreSQL using Drizzle ORM, ensuring data integrity and performance. The platform follows a Monorepo architecture and is designed for Serverless Deployment (e.g., Vercel), allowing managers to start with zero infrastructure costs and scale as needed.

A key innovation element is the integration of Large Language Models (LLMs) via Vercel AI SDK and OpenRouter, offering smart features at multiple levels. Furthermore, an «Auto Actions» mechanism was developed to fully automate communication through multiple channels (Email, OTA Messages, Telegram).

This work contributes to understanding how modern software architectures and Rapid Development tools can transform business processes, delivering high-value solutions with reduced development and maintenance time.

\section{Αντικείμενο της Μελέτης}
\label{sec:subject}

Το αντικείμενο της παρούσας διπλωματικής εργασίας είναι ο σχεδιασμός και η ανάπτυξη ενός ολοκληρωμένου πληροφοριακού συστήματος, του «Lunarety», για τη διαχείριση τουριστικών καταλυμάτων. Η πλατφόρμα δεν αποτελεί απλώς ένα ακόμη PMS, αλλά μια ολιστική λύση που στοχεύει στην κεντρικοποίηση των λειτουργιών που απαιτούνται από επαγγελματίες διαχειριστές (Managers) και τους πελάτες τους, τους ιδιοκτήτες ακινήτων (Owners). Πέρα από τις βασικές λειτουργίες διαχείρισης κρατήσεων και συγχρονισμού ημερολογίων, η πλατφόρμα ενσωματώνει προηγμένες δυνατότητες Τεχνητής Νοημοσύνης (LLMs) για την υποβοήθηση της επικοινωνίας και την παροχή έξυπνων υπηρεσιών.

Κεντρική φιλοσοφία της πλατφόρμας είναι η \textbf{διαχείριση της πολυπλοκότητας ανά ρόλο χρήστη}. Κάθε χρήστης---είτε πρόκειται για Manager, Owner, είτε για απλό προσωπικό (Staff)---αντικρίζει ένα απλό και κατανοητό περιβάλλον εργασίας που περιλαμβάνει μόνο τις πληροφορίες και τις λειτουργίες που αφορούν τον δικό του ρόλο και τις δικές του ευθύνες. Η πολυπλοκότητα του συστήματος παραμένει κρυμμένη από τους χρήστες που δεν χρειάζεται να την γνωρίζουν, ενώ αποκαλύπτεται σταδιακά σε αυτούς που την χρειάζονται. Αυτή η προσέγγιση εξασφαλίζει ότι κάθε χρήστης έχει πλήρη εικόνα για τη δική του εργασία και λογοδοσία, χωρίς να επιβαρύνεται με περιττές πληροφορίες---ένα χαρακτηριστικό που απουσιάζει από τα περισσότερα υπάρχοντα συστήματα PMS.

Επιπλέον, η πλατφόρμα αναγνωρίζει τον \textbf{Property Manager ως εντολοδόχο που δικαιούται προμήθειας}. Τα περισσότερα συστήματα PMS αντιμετωπίζουν τον ιδιοκτήτη ως κάποιον που πληρώνει προμήθεια μόνο στα OTAs (Booking.com, Airbnb), αγνοώντας τη σχέση Manager-Owner. Αυτό αναγκάζει τους Managers να επεξεργάζονται χειροκίνητα τα τιμολόγια και να τα αποστέλλουν στους πελάτες τους. Το Lunarety ενσωματώνει αυτή τη σχέση στον πυρήνα του, αυτοματοποιώντας τον υπολογισμό και την τιμολόγηση των προμηθειών μεταξύ όλων των εμπλεκόμενων μερών.

Τέλος, η πλατφόρμα διαθέτει ένα \textbf{σύγχρονο και διαισθητικό περιβάλλον χρήστη}, σχεδιασμένο να λειτουργεί άψογα τόσο σε desktop όσο και σε κινητές συσκευές. Η διεπαφή ακολουθεί καθιερωμένα πρότυπα UX που είναι οικεία στους χρήστες από εφαρμογές καθημερινής χρήσης, μειώνοντας δραστικά τον χρόνο εκμάθησης ακόμη και για χρήστες που δυσκολεύονται να υιοθετήσουν νέες τεχνολογίες.

\section{Το Κενό στην Αγορά: Managers και Owners}
\label{sec:market-gap}

Η παρούσα εργασία απευθύνεται κυρίως σε επαγγελματίες Property Managers που διαχειρίζονται χαρτοφυλάκια ακινήτων που ανήκουν σε τρίτους (Owners). Στην τρέχουσα αγορά, παρατηρείται ένα σημαντικό κενό:

\begin{itemize}
    \item Οι Managers συχνά αναγκάζονται να χρησιμοποιούν πολύπλοκα λογισμικά Channel Managers, τα οποία είναι δύσχρηστα για τους Owners ή το απλό προσωπικό.
    \item Η ενημέρωση των Owners για κρατήσεις, πληρότητες και οικονομικά στοιχεία γίνεται συχνά χειροκίνητα (τηλέφωνα, excel, emails), οδηγώντας σε λάθη και καθυστερήσεις.
    \item Η δημιουργία λογαριασμών για Owners μέσα στα υπάρχοντα Channel Managers είναι συχνά δαπανηρή ή πολύπλοκη διαδικασία.
    \item Τα υπάρχοντα συστήματα δεν αναγνωρίζουν τον Manager ως εντολοδόχο με δικαίωμα προμήθειας, αναγκάζοντάς τον να διαχειρίζεται χειροκίνητα τη χρέωση και τιμολόγηση των πελατών του.
\end{itemize}

Το Lunarety έρχεται να καλύψει αυτό το κενό, προσφέροντας μια ενδιάμεση, φιλική προς τον χρήστη πλατφόρμα, όπου ο Manager ορίζει τα δικαιώματα, τις συνδρομές και την πρόσβαση των Owners, παρέχοντάς τους ακριβώς την πληροφορία που χρειάζονται σε πραγματικό χρόνο.

\subsection{Αρχιτεκτονική Channel Adapter}
\label{subsec:channel-adapter}

Αντί να αντικαταστήσει τους υπάρχοντες Channel Managers, η πλατφόρμα σχεδιάστηκε ώστε να \textbf{λειτουργεί επιπρόσθετα σε αυτούς} μέσω μιας αρχιτεκτονικής Channel Adapters. Αυτή η προσέγγιση επιτρέπει στους Managers να συνεχίσουν να χρησιμοποιούν τα υπάρχοντα εργαλεία τους (π.χ. Beds24) για τον συγχρονισμό με τα OTAs, ενώ παράλληλα επεκτείνουν τη λειτουργικότητά τους με τα χαρακτηριστικά του Lunarety.

Επί του παρόντος, η πλατφόρμα υποστηρίζει ένα Channel Manager (Beds24), αλλά η αρχιτεκτονική έχει σχεδιαστεί ώστε να επιτρέπει την εύκολη προσθήκη νέων Adapters για επιπλέον Channel Managers στο μέλλον. Κάθε Adapter μεταφράζει τις κλήσεις της πλατφόρμας στο αντίστοιχο API του Channel Manager, διατηρώντας τον υπόλοιπο κώδικα της εφαρμογής ανεξάρτητο από τον συγκεκριμένο πάροχο.

\subsection{TypeScript και Type Consistency}
\label{subsec:typescript}

Η TypeScript~\cite{typescript} είναι ένα superset της JavaScript που προσθέτει στατική τυποποίηση (static typing). Η στατική τυποποίηση εξασφαλίζει «Type Consistency» σε ολόκληρη την εφαρμογή (Fullstack), που σημαίνει ότι τα δεδομένα που επιστρέφει το Backend είναι εγγυημένα συμβατά με αυτά που περιμένει το Frontend. Αυτό μειώνει δραματικά τα runtime errors και επιταχύνει την ανάπτυξη μέσω του IntelliSense. Η TypeScript έχει καθιερωθεί ως το standard για την ανάπτυξη σύγχρονων, κλιμακώσιμων web εφαρμογών.

\subsection{Serverless Architecture}
\label{subsec:serverless}

Η \textbf{Serverless Architecture}~\cite{serverless} αποτελεί ένα μοντέλο cloud computing όπου ο πάροχος (π.χ. AWS, Vercel, Google Cloud) διαχειρίζεται αυτόματα την υποδομή των servers. Παρά το όνομά της, η serverless αρχιτεκτονική δεν σημαίνει απουσία servers -- απλώς ο προγραμματιστής δεν χρειάζεται να τους διαχειρίζεται.

\paragraph{Βασικά Χαρακτηριστικά:}
\begin{itemize}
    \item \textbf{Auto-scaling:} Η υποδομή κλιμακώνεται αυτόματα ανάλογα με το φορτίο. Από μηδέν instances όταν δεν υπάρχει traffic, έως χιλιάδες όταν απαιτείται.
    \item \textbf{Pay-per-use:} Η χρέωση γίνεται βάσει πραγματικής χρήσης (αριθμός εκτελέσεων, χρόνος εκτέλεσης) αντί για σταθερό μηνιαίο κόστος server.
    \item \textbf{Zero DevOps:} Δεν απαιτείται διαχείριση servers, patches, ή υποδομής -- ο προγραμματιστής εστιάζει μόνο στον κώδικα.
    \item \textbf{Event-driven:} Οι συναρτήσεις εκτελούνται ως απάντηση σε events (HTTP requests, database triggers, scheduled tasks).
\end{itemize}

\paragraph{Functions as a Service (FaaS):}
Το κυριότερο μοντέλο serverless είναι το \textbf{FaaS}, όπου ο κώδικας οργανώνεται σε μικρές, ανεξάρτητες συναρτήσεις. Κάθε συνάρτηση εκτελείται σε απομονωμένο περιβάλλον, ξεκινά όταν καλείται (cold start), και τερματίζεται μετά την ολοκλήρωση.

\paragraph{Πλεονεκτήματα και Περιορισμοί:}
\begin{description}
    \item[Πλεονεκτήματα:] Μηδενικό αρχικό κόστος υποδομής, αυτόματη κλιμάκωση, μειωμένη πολυπλοκότητα deployment, ιδανικό για startups και MVPs.
    \item[Περιορισμοί:] Cold starts (καθυστέρηση κατά την πρώτη κλήση), όρια χρόνου εκτέλεσης (συνήθως 10-60 δευτερόλεπτα), περιορισμένος έλεγχος υποδομής.
\end{description}

Πλατφόρμες όπως η \textbf{Vercel}, το \textbf{AWS Lambda}, και το \textbf{Google Cloud Functions} αποτελούν δημοφιλείς παρόχους serverless υπηρεσιών για web εφαρμογές.

\subsection{Next.js: Ένα Full-Stack React Framework}
\label{subsec:nextjs}

Το Next.js~\cite{nextjs} είναι ένα open-source React framework που αναπτύσσεται και συντηρείται από την Vercel. Προσφέρει δυνατότητες Server-Side Rendering (SSR) και Static Site Generation (SSG), καθιστώντας το ιδανικό για Serverless deployments~\cite{serverless}. Η αρχιτεκτονική του επιτρέπει σε frameworks όπως το PayloadCMS v3 να τρέχουν εντός του, δημιουργώντας ένα ενοποιημένο full-stack περιβάλλον.

\begin{description}
    \item[Server Actions:] Μια λειτουργία που επιτρέπει στο Frontend να καλεί συναρτήσεις του Backend απευθείας, χωρίς την ανάγκη ρητού ορισμού API Endpoints. Αυτό απλοποιεί τη διαχείριση δεδομένων και διατηρεί την τυποποίηση (types) από άκρη σε άκρη.
    \item[Monorepo Architecture:] Η δομή του Next.js υποστηρίζει τη διατήρηση όλου του κώδικα (Frontend, Backend, Webhooks) σε ένα ενιαίο Repository, επιτρέποντας την κοινή χρήση τύπων και utilities και εξαλείφοντας την ανάγκη για συγχρονισμό μεταξύ διαφορετικών projects.
    \item[Local API:] Όταν συνδυάζεται με CMS frameworks όπως το PayloadCMS, το Next.js υποστηρίζει \code{localAPI} -- τυποποιημένη (typed) πρόσβαση στη βάση δεδομένων από οποιαδήποτε server function. Αυτό επιτρέπει κλήσεις όπως \code{payload.find()}, \code{payload.create()}, \code{payload.update()} με πλήρες autocomplete και type-checking, χωρίς HTTP requests.
\end{description}

\subsubsection{CollectionConfig: Ο Ενιαίος Ορισμός}
\label{subsubsec:collectionconfig}

Το κεντρικό concept του PayloadCMS είναι το \textbf{CollectionConfig}. Ένα μόνο αντικείμενο TypeScript ορίζει ταυτόχρονα:

\begin{enumerate}
    \item \textbf{Το σχήμα της βάσης δεδομένων (ORM):} Παρόμοια με τα Django Models ή τα Laravel Eloquent Models, τα fields ορίζουν τις στήλες του πίνακα.
    \item \textbf{Το REST/GraphQL API:} Αυτόματη δημιουργία endpoints για CRUD operations.
    \item \textbf{Τη διεπαφή διαχείρισης (Admin UI):} Ένα πλήρως λειτουργικό admin panel που παράγεται αυτόματα.
    \item \textbf{Τη συμπεριφορά και τη λογική:} Hooks, access control, validation---όλα μέσα στο ίδιο config.
\end{enumerate}

Το PayloadCMS υποστηρίζει πλούσιες σχέσεις μεταξύ collections μέσω του \code{relationship} field type. Υποστηρίζονται one-to-one, one-to-many, και many-to-many σχέσεις, καθώς και polymorphic relations (ένα πεδίο που μπορεί να δείχνει σε πολλαπλά collections).

Το \code{join} field είναι ιδιαίτερα χρήσιμο καθώς δημιουργεί «virtual» πεδία που δεν αποθηκεύονται στη βάση αλλά υπολογίζονται δυναμικά. Η παράμετρος \code{where} επιτρέπει φιλτράρισμα των σχετιζόμενων εγγραφών.

\newpage
\begin{lstlisting}[caption={Παράδειγμα CollectionConfig με custom components και conditional logic},basicstyle=\scriptsize\ttfamily,aboveskip=0pt,belowskip=0pt,lineskip=0pt]
import { CollectionConfig } from 'payload/types';
import { CustomPriceEditor } from './components/CustomPriceEditor';

export const Bookings: CollectionConfig = {
  slug: 'bookings',
  // Access control
  access: {
    read: ({ req: { user } }) => {
      return true;
    },
  },
  // Database schema + UI fields
  fields: [
    {
      name: 'mainBooking',
      type: 'relationship',
      relationTo: 'bookings',
      required:false,
      // filterOptions: Dynamic filtering based on user
      filterOptions: ({ user }) => ({
        manager: { equals: user.id },
      }),
    },
    {
      name:'relatedBookings',
      type: 'join',
      collection: 'bookings',
      on: 'mainBooking',
      where: {
        status: {
          not_in: ['cancelled'],
        },
      },
    },
    {
      name: 'totalAmount',
      type: 'number',
      required: true,
      admin: {
        // Custom React component for the Admin UI
        components: {
          Field: CustomPriceEditor,
        },
        // Conditional display: only show if user has permission
        condition: (data, siblingData, { user }) => {
          return user.settings.bookings.canModifyPrices
        },
      },
    },
  ],
};
\end{lstlisting}

\newpage
Στο παραπάνω παράδειγμα:

\begin{itemize}
    \item Το \code{relationship} field type δημιουργεί σχέσεις μεταξύ collections, υποστηρίζοντας one-to-one, one-to-many, και many-to-many relations.
    \item Το \code{join} field δημιουργεί «virtual» πεδία που υπολογίζονται δυναμικά χωρίς να αποθηκεύονται στη βάση, συνδέοντας εγγραφές μέσω της παράμετρου \code{on} και φιλτράροντας με \code{where}.
    \item Το \code{filterOptions} φιλτράρει δυναμικά τις επιλογές ενός relationship field βάσει του χρήστη ή άλλων παραμέτρων.
    \item Το \code{admin.components.Field} επιτρέπει την αντικατάσταση του default input με ένα custom React component (\code{CustomPriceEditor}).
    \item Το \code{admin.condition} καθορίζει πότε ένα πεδίο είναι ορατό στο UI βάσει δυναμικής λογικής (π.χ. δικαιώματα χρήστη).
\end{itemize}

\subsubsection{Lifecycle Hooks και Direct Database Access}
\label{subsubsec:lifecycle-hooks}

Το PayloadCMS παρέχει ένα ισχυρό σύστημα hooks που επιτρέπει την εκτέλεση κώδικα σε συγκεκριμένα σημεία του κύκλου ζωής ενός document:

\begin{itemize}
    \item \code{beforeValidate}, \code{beforeChange}, \code{beforeRead}, \code{beforeDelete}
    \item \code{afterChange}, \code{afterRead}, \code{afterDelete}
\end{itemize}

Ωστόσο, για operations μεγάλης κλίμακας (mass imports), τα hooks μπορούν να δημιουργήσουν σημαντικό overhead. Για αυτό το λόγο, το PayloadCMS επιτρέπει \textbf{απευθείας πρόσβαση στη βάση δεδομένων}:

\begin{lstlisting}[caption={Standard Lifecycle vs Direct Database Access}]
// STANDARD: Full lifecycle - hooks execute, validation runs
const booking = await payload.create({
  collection: 'bookings',
  data: bookingData,
});

// DIRECT DB: Bypass lifecycle - for mass operations
// Uses Drizzle ORM under the hood
await payload.db.create({
  collection: 'bookings',
  data: dtoPayloadToPayloadDb(bookingData),
});

// Even lower level: Direct Drizzle access
const db = payload.db.drizzle;
await db.insert(bookingsTable).values(bookingsArray);
\end{lstlisting}

Αυτή η ευελιξία είναι κρίσιμη για την απόδοση. Κατά την αρχική εισαγωγή ενός Manager (με χιλιάδες rates και bookings), η χρήση του \code{payload.db} αντί του \code{payload.create()} μπορεί να μειώσει τον χρόνο εκτέλεσης από ώρες σε λεπτά.

\subsubsection{Drizzle ORM: Type-Safe Database Access}
\label{subsubsec:drizzle-orm}

Το \textbf{Drizzle ORM}~\cite{drizzle} είναι ένα σύγχρονο, ελαφρύ TypeScript ORM που χρησιμοποιείται από το PayloadCMS v3 για την επικοινωνία με τη βάση δεδομένων. Τα χαρακτηριστικά του περιλαμβάνουν:

\begin{itemize}
    \item Αυτόματη παραγωγή TypeScript types από το schema
    \item Δυνατότητα raw SQL queries όταν χρειάζεται
    \item Υποστήριξη migrations για εξέλιξη του schema
    \item Υψηλή απόδοση συγκριτικά με βαρύτερα ORMs (όπως το Prisma)
\end{itemize}

\subsection{PostgreSQL: Σχεσιακή Βάση Δεδομένων}
\label{subsec:postgresql}

Η PostgreSQL~\cite{postgresql} είναι μια ισχυρή, open-source σχεσιακή βάση δεδομένων με δεκαετίες ανάπτυξης. Υποστηρίζεται από το PayloadCMS v3 ως η κύρια βάση δεδομένων (αντικαθιστώντας τη MongoDB που υποστηριζόταν στην έκδοση).

\begin{description}
    \item[ACID Transactions:] Η PostgreSQL εγγυάται Atomicity, Consistency, Isolation, Durability -- κρίσιμο για εφαρμογές που απαιτούν συνέπεια δεδομένων κατά τον συγχρονισμό με εξωτερικά συστήματα.
    \item[Complex Queries:] Η σχεσιακή δομή επιτρέπει πολύπλοκες αναζητήσεις (JOINs, aggregations) που είναι πιο αποδοτικές από τα αντίστοιχα document-based queries.
    \item[Relational Integrity:] Υποστηρίζει foreign keys και referential integrity για αυστηρές σχέσεις μεταξύ οντοτήτων.
\end{description}

\subsection{Shadcn UI, React και Zustand}

\section{Channel Managers και Διασυνδεσιμότητα}

\subsection{Τι είναι ο Channel Manager}
\label{subsec:what-is-channel-manager}

Ο \textbf{Channel Manager}~\cite{pms_systems} είναι ένα λογισμικό που λειτουργεί ως ενδιάμεσος κόμβος μεταξύ των καταλυμάτων και των Online Travel Agencies (OTAs) όπως το Airbnb, το Booking.com, η Expedia, και η Vrbo. Ο κύριος ρόλος του είναι να διατηρεί \textbf{συγχρονισμένες τις τιμές και τη διαθεσιμότητα} σε όλα τα κανάλια πώλησης σε πραγματικό χρόνο.

\begin{figure}[H]
    \centering
    \includegraphics[frame=0.5pt,width=\textwidth]{images/channel_manager_infographic.png}
    \caption{Αρχιτεκτονική Channel Manager ως ενδιάμεσου κόμβου.}
    \label{fig:channel-manager-arch}
\end{figure}

\paragraph{Βασικές Λειτουργίες Channel Manager:}

\begin{itemize}
    \item \textbf{Συγχρονισμός Διαθεσιμότητας:} Όταν ένα δωμάτιο κλείνει στο Airbnb, ο Channel Manager ενημερώνει αυτόματα το Booking.com και όλα τα άλλα συνδεδεμένα κανάλια ότι το δωμάτιο δεν είναι πλέον διαθέσιμο. Αυτό αποτρέπει τις overbookings.
    \item \textbf{Συγχρονισμός Τιμών:} Επιτρέπει τον ορισμό τιμών από ένα κεντρικό σημείο, οι οποίες διανέμονται σε όλα τα κανάλια.
    \item \textbf{Κεντρική Διαχείριση Κρατήσεων:} Όλες οι κρατήσεις από διαφορετικά κανάλια συγκεντρώνονται σε ένα σημείο.
    \item \textbf{Επικοινωνία με Guests:} Πολλοί Channel Managers προσφέρουν unified inbox για μηνύματα από όλα τα κανάλια.
\end{itemize}

\subsection{Γιατί είναι Απαραίτητοι οι Channel Managers}
\label{subsec:why-channel-managers}

Ένα κρίσιμο ερώτημα είναι: \textit{Γιατί δεν συνδέονται τα PMS απευθείας με τα OTAs;} Η απάντηση είναι πολύπλευρη:

\begin{enumerate}
    \item \textbf{Περιορισμένη Πρόσβαση σε APIs:} Τα μεγάλα OTAs όπως το \textbf{Airbnb} και το \textbf{Booking.com} δεν παρέχουν δημόσια API access σε τρίτους developers. Η πρόσβαση στα APIs τους απαιτεί:
    \begin{itemize}
        \item Εγκεκριμένη συνεργασία (Partnership Agreement)
        \item Αυστηρές διαδικασίες πιστοποίησης
        \item Ελάχιστο volume κρατήσεων (συνήθως χιλιάδες ανά μήνα)
        \item Νομική οντότητα και ασφάλιση
    \end{itemize}
    Αυτό καθιστά την απευθείας σύνδεση αδύνατη για τις περισσότερες εταιρείες και startups.
    
    \item \textbf{Τεχνική Πολυπλοκότητα:} Κάθε OTA έχει διαφορετικό API format, authentication mechanism, και business logic. Η υποστήριξη πολλαπλών OTAs απευθείας θα απαιτούσε τεράστια προσπάθεια ανάπτυξης και συντήρησης.
    
    \item \textbf{Reliability και Support:} Οι Channel Managers έχουν dedicated teams για τη διατήρηση της σύνδεσης με τα OTAs, την αντιμετώπιση API changes, και την επίλυση προβλημάτων.
\end{enumerate}

\paragraph{Παράδειγμα Πρακτικής Εφαρμογής:}
Ένα τυπικό PMS δεν μπορεί να λάβει απευθείας API access από το Airbnb ή το Booking.com. Ωστόσο, μέσω της σύνδεσης με έναν Channel Manager (όπως το Beds24), αποκτά πρόσβαση σε όλες τις κρατήσεις και τα μηνύματα από αυτά τα κανάλια. Ο Channel Manager λειτουργεί ως «γέφυρα» που μεταφράζει τις κλήσεις του PMS σε κλήσεις προς τα OTAs.

\subsection{Beds24: Ένας Δημοφιλής Channel Manager}
\label{subsec:beds24}

Το \textbf{Beds24}~\cite{beds24api} είναι ένας από τους πιο διαδεδομένους Channel Managers στην αγορά, με ιδιαίτερη δημοτικότητα στην Ευρώπη. Τα κύρια χαρακτηριστικά του περιλαμβάνουν:

\begin{enumerate}
    \item \textbf{Modern API:} Διαθέτει σύγχρονο, comprehensive API με υποστήριξη OpenAPI specification, επιτρέποντας την αυτόματη παραγωγή κώδικα (μέσω εργαλείων όπως το \code{swagger-typescript-api}).
    \item \textbf{Webhook Support:} Υποστηρίζει real-time webhooks για νέες κρατήσεις και μηνύματα, επιτρέποντας instant ενημερώσεις αντί για polling.
    \item \textbf{Πλήρες Feature Set:} Υποστηρίζει τιμές ανά ημέρα, restrictions (min/max stay), μηνύματα guests, και σύνδεση με πολλαπλά κανάλια (Airbnb, Booking.com, κ.α.).
    \item \textbf{Ανταγωνιστική Τιμολόγηση:} Προσφέρει οικονομικές επιλογές συγκριτικά με άλλους Channel Managers της αγοράς.
\end{enumerate}

\section{Ρόλοι και Ιεραρχία Χρηστών}
\label{sec:user-hierarchy}

Το σύστημα σχεδιάστηκε με γνώμονα την ιεραρχία Manager-Owner:

\begin{enumerate}
    \item \textbf{Platform Users (Admins):} Οι διαχειριστές της πλατφόρμας Lunarety. Έχουν καθολική εποπτεία.
    \item \textbf{Managers:} Ο κεντρικός κόμβος. Συνδέουν το Channel Manager τους, δημιουργούν πλάνα χρέωσης και εισάγουν τους Owners τους. Η πρόσβαση τους καθορίζεται αυστηρά απο τους Platform Users.
    \item \textbf{Owners:} Πελάτες του Manager. Βλέπουν μόνο τα δικά τους ακίνητα και οικονομικά στοιχεία. Η πρόσβασή τους καθορίζεται αυστηρά από τον Manager.
    \item \textbf{Staff:} Υπάλληλοι (καθαριστές, υποδοχή) που ανήκουν σε Manager ή προαιρετικά και σε Owner, με περιορισμένα δικαιώματα. Η πρόσβασή τους καθορίζεται αυστηρά από τον Manager ή Owner τους.
\end{enumerate}

Το σύστημα υλοποιεί ένα εύκαμπτο μοντέλο δικαιωμάτων που επιτρέπει τον έλεγχο σε κάθε επίπεδο.

    \item Δημιουργία Staff που ανήκουν σε αυτούς *

\paragraph{Staff:}
\begin{itemize}

    \item Χρήσιμοι για εργασίες καθαρισμού, check-in, κ.λπ.
\end{itemize}

Όπως φαίνεται στο διάγραμμα, κάθε collection έχει το δικό του \code{on:change} trigger που ενεργοποιεί διαφορετικές διαδρομές ανάλογα με τις συνθήκες. Τα βασικά αρχιτεκτονικά patterns που προκύπτουν από αυτή τη σχεδίαση είναι τα εξής:

\subsection{Βασικά Αρχιτεκτονικά Patterns}
\label{subsec:lifecycle-patterns}

\paragraph{Στρατηγική «Κύματος» (Ripple Effect):}
Η αρχιτεκτονική είναι σχεδιασμένη ώστε μια αλλαγή στο ανώτερο επίπεδο να διαδίδεται προς τα κάτω στη μικρότερη μονάδα (το Rate). Τόσο οι αλλαγές σε Properties όσο και σε Bookings καταλήγουν να ενεργοποιούν το lifecycle των \code{propertyRates}, διασφαλίζοντας ότι η λογική τιμολόγησης είναι πάντα ακριβής.

\paragraph{Αποτροπή Βρόχων (\code{skipChannelSync}):}
Ο αμφίδρομος συγχρονισμός (Local DB $\leftrightarrow$ Beds24) είναι επιρρεπής σε «ηχώ». Το \code{skipChannelSync} flag αποτρέπει το σύστημα από το να προσπαθήσει να ενημερώσει πίσω τον Channel Manager με δεδομένα που μόλις έλαβε από αυτόν.

\paragraph{Ισορροπία Απόδοσης vs Ακρίβειας:}
Σε πολλά ORMs, η εκτέλεση \code{updateMany} παρακάμπτει τα lifecycle hooks. Το σύστημα εκτελεί τις ενημερώσεις rates «ένα-ένα» για να διασφαλίσει ότι οι event listeners ενεργοποιούνται για κάθε record. Αν και αυτή η προσέγγιση είναι αργή, συνήθως εκτελείται μόνο μία φορά ανά Property κατά το onboarding.

\paragraph{Διαχείριση Κατάστασης (State Management):}
Η διάκριση μεταξύ \code{imported} και \code{active} properties επιτρέπει την ασφαλή εισαγωγή δεδομένων από τον Channel Manager (staging) πριν ξεκινήσει η επεξεργασία live κρατήσεων.

Με αυτή την αρχιτεκτονική ως βάση, οι επόμενες ενότητες αναλύουν λεπτομερώς τις επιμέρους υλοποιήσεις κάθε λειτουργίας.

\section{Διαχείριση Κρατήσεων και Συγχρονισμός}
\label{sec:booking-sync}

Η διασύνδεση με το Beds24 είναι κρίσιμη και ακολουθεί μια συγκεκριμένη ροή:

\begin{enumerate}
    \item \textbf{Σύνδεση Λογαριασμού:} Ο Manager εισάγει το API Key του Beds24.
    \item \textbf{Token Refresh:} Μια φορά την ημέρα και κατα το Initialization γίνεται αυτόματη ανανέωση του Beds24 token κάθε Manager μέσω του refresh token, ώστε να διασφαλίζεται απρόσκοπτη επικοινωνία με το Channel Manager.
    \item \textbf{Initial Import:} Κατά την εισαγωγή του κλειδιού, το σύστημα εκτελεί μια μαζική εισαγωγή (Import) όλων των Properties και των Rates που είναι ορισμένα στο Channel Manager.
    \item \textbf{Webhook Configuration:} Το σύστημα αυτόματα ενημερώνει τις ρυθμίσεις του Channel Manager (Beds24) ώστε να στέλνει Webhooks στο endpoint της πλατφόρμας (\code{/api/webhooks/channel-managers/beds24/bookings}).
    \item \textbf{Async Updates:} Από εκείνη τη στιγμή, κάθε αλλαγή (νέα κράτηση, αλλαγή ημερομηνίας) έρχεται ασύγχρονα μέσω Webhook.
\end{enumerate}

Η διαχείριση κρατήσεων αποτελεί τον πυρήνα της πλατφόρμας και απαιτεί προσεκτικό σχεδιασμό για να εξασφαλιστεί η ακεραιότητα των δεδομένων, η απόδοση και η συνέπεια μεταξύ της τοπικής βάσης δεδομένων και του Channel Manager.

\subsection{Αρχική Σύνδεση και Ρύθμιση Webhooks}
\label{subsec:initial-connection}

\begin{enumerate}
    \item \textbf{Σύνδεση Λογαριασμού:} Ο Manager εισάγει το Refresh Token του Beds24 στις ρυθμίσεις του λογαριασμού του.
    \item \textbf{Token Exchange:} Το σύστημα αυτόματα ανταλλάσσει το Refresh Token για ένα Access Token μέσω του \code{b24ApiRefreshToken()}.
    \item \textbf{User ID Retrieval:} Ανακτάται το \code{channelManagerUserId} από το Beds24.

\end{enumerate}

\subsubsection{Α) Mass Import (Property Syncing)}

Η \textbf{μαζική εισαγωγή bookings} πραγματοποιείται όταν ένα Property μεταβαίνει από την κατάσταση \code{imported} στην \code{active} (ενεργοποίηση του καταλύματος). Κατά τη διαδικασία αυτή, η πλατφόρμα χρειάζεται να εισάγει εκατοντάδες ή χιλιάδες κρατήσεις από το Beds24. Χρησιμοποιείται η \code{payload.db.create()} και \code{payload.db.updateOne()} αντί των standard methods, παρακάμπτοντας τα hooks για βέλτιστη απόδοση.

\begin{lstlisting}[caption={Mass import με direct DB operations}]
const syncBookingsOperations = async (
  bookingsToCreate: RequiredDataFromCollectionSlug<"bookings">[],
  bookingsToUpdate: Array<{
    id: number;
    data: RequiredDataFromCollectionSlug<"bookings">;
  }>,
  bookingsToDelete: Booking[]
) => {
  // CREATE - Direct DB, bypassing lifecycle
  for (const booking of bookingsToCreate) {
    await payload.db.create({
      collection: "bookings",
      data: dtoPayloadToPayloadDb(booking),
    });
  }

  // UPDATE - Direct DB, bypassing lifecycle
  for (const { id, data } of bookingsToUpdate) {
    await payload.db.updateOne({
      collection: "bookings",
      id: id,
      data: dtoPayloadToPayloadDb(data),
    });
  }
};
\end{lstlisting}

Μετά την εισαγωγή των bookings, ενεργοποιείται η ενημέρωση \textbf{όλων των σχετικών PropertyRates} για να αντικατοπτριστεί η διαθεσιμότητα. Αν και αυτή η διαδικασία δεν είναι βέλτιστη (καθώς ενεργοποιεί mass updates σε χιλιάδες rate records), δεν έχει αναπτυχθεί ακόμα χαμηλότερου επιπέδου υλοποίηση -- η βελτιστοποίηση αυτή αναλύεται στην Ενότητα \ref{subsec:property-import}.

Σημειώνεται ότι η μαζική εισαγωγή \textbf{εκτελείται μόνο μία φορά} κατά την ενεργοποίηση του property. Μετά την αρχική εισαγωγή, όλες οι ενημερώσεις (δημιουργία, τροποποίηση, ακύρωση κρατήσεων) λαμβάνονται μέσω \textbf{webhooks} σε πραγματικό χρόνο, οπότε η απόδοση είναι ικανοποιητική.

\subsection{Διαχείριση Ημερομηνιών και Ζωνών Ώρας}
\label{subsec:date-timezone-management}

Ένα κρίσιμο τεχνικό ζήτημα στη διαχείριση κρατήσεων αφορά την αναπαράσταση και επεξεργασία ημερομηνιών. Η πλατφόρμα υιοθετεί μια συγκεκριμένη στρατηγική που διασφαλίζει συνέπεια και απλοποιεί τους υπολογισμούς.

\subsubsection{Αριθμητική Αναπαράσταση Ημερομηνιών (YYYYMMDD)}

Οι ημερομηνίες στην πλατφόρμα αποθηκεύονται ως \textbf{αριθμοί} στη μορφή \code{YYYYMMDD}. Για παράδειγμα:
\begin{itemize}
    \item Η 31η Δεκεμβρίου 2025 αποθηκεύεται ως \code{20251231}
    \item Η 1η Ιανουαρίου 2026 αποθηκεύεται ως \code{20260101}
\end{itemize}

\textbf{Πλεονεκτήματα αυτής της προσέγγισης:}
\begin{itemize}
    \item \textbf{Απλές συγκρίσεις:} Η σύγκριση ημερομηνιών γίνεται με απλές αριθμητικές πράξεις (\code{date1 < date2})
    \item \textbf{Αποτελεσματικό indexing:} Οι αριθμητικοί δείκτες στη βάση δεδομένων είναι ταχύτεροι
    \item \textbf{Αποφυγή timezone bugs:} Δεν υπάρχει κίνδυνος μετατόπισης ημέρας λόγω timezone conversions
    \item \textbf{Συμβατότητα με Beds24:} Το Channel Manager χρησιμοποιεί την ίδια μορφή
\end{itemize}

\begin{lstlisting}[caption={Μετατροπή ημερομηνίας σε αριθμητική μορφή}]
// Μετατροπή Date σε αριθμητική μορφή YYYYMMDD
const dateToNumber = (date: Date): number => {
  return Number(format(date, "yyyyMMdd")); // π.χ. 20251231
};

// Αντίστροφη μετατροπή
const numberToDate = (dateNum: number): Date => {
  const str = dateNum.toString();
  return parse(str, "yyyyMMdd", new Date());
};
\end{lstlisting}

\subsubsection{Υπολογισμός Ακριβούς Ώρας Check-In}

Κάθε Property έχει μια \textbf{ζώνη ώρας} (\code{timezone}) και μια \textbf{προεπιλεγμένη ώρα check-in} (\code{defaultCheckInTime}). Αυτά τα πεδία είναι κρίσιμα για τον υπολογισμό της ακριβούς στιγμής που θα πρέπει να εκτελεστούν οι αυτοματισμοί (Auto Actions).

\begin{lstlisting}[caption={Υπολογισμός ακριβούς ώρας check-in}]
// Υπολογισμός ακριβούς checkIn timestamp
const calculateExactCheckInTime = (
  checkInDate: number,      // π.χ. 20251231
  property: Property
): Date => {
  const timezone = property.timezone ?? "Europe/Athens";
  const checkInTime = property.defaultCheckInTime ?? "15:00";
  
  // Συνδυασμός ημερομηνίας και ώρας στη ζώνη ώρας του property
  const dateStr = checkInDate.toString(); // "20251231"
  const localDateTime = `${dateStr.slice(0,4)}-${dateStr.slice(4,6)}-${dateStr.slice(6,8)}T${checkInTime}`;
  
  // Μετατροπή σε UTC για αποθήκευση
  return fromZonedTime(localDateTime, timezone);
};
\end{lstlisting}

\textbf{Παράδειγμα:} Έστω ένα κατάλυμα στην Αθήνα (\code{Europe/Athens}) με \code{defaultCheckInTime: "15:00"} και κράτηση με \code{checkIn: 20251231}:
\begin{enumerate}
    \item Η τοπική ώρα check-in είναι: 31/12/2025 στις 15:00 (ώρα Αθήνας)
    \item Μετατρέπεται σε UTC: 31/12/2025 στις 13:00 (UTC+2 το χειμώνα)
    \item Αποθηκεύεται ως \code{checkInStartOfDay} στο booking
\end{enumerate}

Αυτή η προσέγγιση είναι ιδιαίτερα σημαντική για τα \textbf{Time-based Triggers} των Auto Actions (βλ. Ενότητα \ref{subsec:time-based-triggers}), καθώς επιτρέπει τον ακριβή υπολογισμό του πότε πρέπει να σταλεί ένα μήνυμα (π.χ. «2 ώρες πριν το check-in»).

\subsection{Σύστημα Σύνδεσης με Property Rates}
\label{subsec:rate-linking}

Κάθε κράτηση συνδέεται με τα αντίστοιχα PropertyRate records μέσω του \code{relatedRates} field. Αυτό είναι κρίσιμο για:

\begin{itemize}
    \item Τον υπολογισμό διαθεσιμότητας (π.χ. ένα rate με 3 units και με 3 booked unit δεν είναι διαθέσιμο)
    \item Την ενημέρωση του ημερολογίου
\end{itemize}

\paragraph{linkRatesToBooking Hook:} Για να διασφαλίσουμε ότι κάθε κράτηση συνδέεται με τα σωστά property rates, χρησιμοποιούμε το hook \texttt{linkRatesToBooking}. Αυτό το hook, κατά τη δημιουργία ή την επεξεργασία μιας κράτησης, εντοπίζει και συσχετίζει με την κράτηση όλα τα rate που αφορούν τις επιλεγμένες ημερομηνίες διαμονής (\texttt{checkIn}, \texttt{checkOut}).

\begin{lstlisting}[caption={linkRatesToBooking Hook}]
export const linkRatesToBooking: CollectionBeforeChangeHook<Booking> = async ({
  data,
  req,
}) => {
  // Εύρεση σχετικών rates για τη διάρκεια της κράτησης
  const rates = await payload.find({
    collection: "property-rates",
    where: {
      channelRoomId: { equals: data.resource.roomAndUnit.roomId },
      date: {
        greater_than_equal: data.resource.checkIn,
        less_than: data.resource.checkOut,
      },
    },
    limit: 10000,
  });

  data.relatedRates = {
    nightlyRates: rates.docs.map((rate) => rate.id),
    checkInRate: rates.docs.find((rate) => rate.date === data.resource.checkIn)
      ?.id,
  };
  return data;
};
\end{lstlisting}

\paragraph{touchNightlyRates Hook (Cascade Update):}

Μετά την αποθήκευση μιας κράτησης, χρειάζεται να ενημερωθούν τα σχετικά rates ώστε να αντικατοπτρίζουν τη νέα κατάσταση. Αυτό γίνεται με ένα «touch» update:

\begin{lstlisting}[caption={touchNightlyRates Hook}]
export const touchNightlyRates: CollectionAfterChangeHook<Booking> = async ({
  doc,
  req,
}) => {
  const rateIds =
    doc.relatedRates?.nightlyRates?.map((rate) =>
      typeof rate === "object" ? rate.id : rate
    ) || [];

  // "Touch" update - ενεργοποιεί τα hooks του property-rates
  await Promise.all(
    rateIds.map((id) =>
      payload.update({
        collection: "property-rates",
        id,
        data: {}, // Κενό update, μόνο για να τρέξουν τα hooks
        req: { transactionID: req.transactionID },
      })
    )
  );
  return doc;
};
\end{lstlisting}

\subsection{Εισαγωγή Properties και Βελτιστοποίηση Property Rates}
\label{subsec:property-import}

Η εισαγωγή καταλυμάτων και των τιμών τους αποτελεί μία από τις πιο απαιτητικές λειτουργίες σε επίπεδο απόδοσης. Για ένα τυπικό κατάλυμα με 4 δωμάτια, το σύστημα χρειάζεται να εισάγει περίπου 5.840 records (4 δωμάτια $\times$ 1.460 ημέρες = 4 χρόνια rates).

\paragraph{Μαζικές Εισαγωγές και Απευθείας Πρόσβαση στη Βάση:}

Γενικά, για τις μαζικές εισαγωγές (mass imports) -- είτε πρόκειται για bookings είτε για properties και rates -- χρησιμοποιούνται \textbf{custom algorithms που δεν βασίζονται καθόλου σε lifecycle hooks} και προσπελαύνουν απευθείας τη βάση δεδομένων. Αυτή η προσέγγιση είναι απαραίτητη για λόγους απόδοσης, καθώς η εκτέλεση του πλήρους lifecycle για χιλιάδες records θα ήταν απαγορευτικά αργή.

\paragraph{Αρχικοποίηση και Καθημερινή Συντήρηση:}

Η μαζική εισαγωγή properties και rates πραγματοποιείται κατά την \textbf{αρχική σύνδεση} (initialization) του Manager με τον Channel Manager. Επιπλέον, τα \textbf{access tokens ανανεώνονται καθημερινά} μέσω του \code{everyNightCron}, διασφαλίζοντας την αδιάλειπτη επικοινωνία με το Beds24 API.

\paragraph{Στρατηγική Εισαγωγής Rates:}

Το σύστημα εισάγει τιμές για ένα παράθυρο 4 ετών (2 χρόνια πίσω + 2 χρόνια μπροστά) για κάθε δωμάτιο. Το Beds24 στέλνει τα rates σε συμπτυγμένη μορφή (date ranges), π.χ. «από 1/1 έως 31/1 με τιμή €100», τα οποία το σύστημα επεκτείνει σε μεμονωμένες ημέρες.

\paragraph{Ευρετηρίαση (Indexing) για Βελτιστοποίηση:}

Ο πίνακας \textbf{PropertyRates έχει ευρετηριαστεί (indexed)} στα πεδία που διαβάζονται και ενημερώνονται πιο συχνά, όπως το \code{date} και το \code{channelRoomId}. Αυτό είναι κρίσιμο διότι όταν ενημερώνεται ένα booking, το σύστημα χρειάζεται να ενημερώσει \textbf{όλα τα προηγούμενα και τρέχοντα related rates} -- μια λειτουργία που εκτελείται πολύ συχνά.

\paragraph{Ενημέρωση Rates κατά την Εισαγωγή:}

Κατά την εισαγωγή ή τον συγχρονισμό, ενημερώνονται \textbf{όλα τα room rates του property}. Αυτή είναι μια βαριά λειτουργία (ενδεχομένως χιλιάδες records), και για αυτό χρησιμοποιείται ειδικός αλγόριθμος που προσπελαύνει απευθείας τη βάση δεδομένων χωρίς να ενεργοποιεί το lifecycle για κάθε record ξεχωριστά.

\paragraph{Αλγόριθμος Σύγκρισης Rates:}

Κατά τον συγχρονισμό, το σύστημα συγκρίνει τα νέα rates με τα υπάρχοντα στη βάση, δημιουργώντας maps για γρήγορη αναζήτηση και κατηγοριοποιώντας τα rates σε: \code{ratesToCreate} (νέα), \code{ratesToUpdate} (τροποποιημένα), και \code{ratesToDelete} (διαγραμμένα).

\paragraph{Γιατί η Τρέχουσα Υλοποίηση είναι Αποδεκτή:}

Παρά τα περιθώρια βελτιστοποίησης, η τρέχουσα υλοποίηση είναι \textbf{αποδεκτή για το παρόν} επειδή η μαζική εισαγωγή rates \textbf{εκτελείται μόνο μία φορά} κατά την αρχική σύνδεση με τον Channel Manager. Αντίστοιχα, η μαζική εισαγωγή bookings (βλ. Ενότητα \ref{subsec:booking-import-methods}) εκτελείται επίσης μόνο μία φορά κατά την ενεργοποίηση του property. Μετά την αρχική εισαγωγή, οι καθημερινές ενημερώσεις γίνονται μεμονωμένα μέσω webhooks, οπότε η απόδοση είναι ικανοποιητική.

\paragraph{Μελλοντική Βελτιστοποίηση:}

Για περαιτέρω βελτίωση της απόδοσης, η παράκαμψη των hooks \textbf{δεν είναι αρκετή} -- απαιτούνται \textbf{mass upsert operations} απευθείας στη βάση δεδομένων. Το Payload CMS υποστηρίζει πρόσβαση στο Drizzle ORM μέσω του \code{payload.db.drizzle}, που επιτρέπει type-safe SQL operations με δυνατότητα batch upserts.

Ωστόσο, αυτή η υλοποίηση \textbf{αποφεύγεται προσωρινά} για τους εξής λόγους:
\begin{itemize}
    \item Κατά τη φάση ανάπτυξης, το schema υφίσταται συχνές αλλαγές (breaking changes).
    \item Η χρήση low-level SQL/Drizzle queries απαιτεί σταθερό schema για να αποφευχθούν runtime errors.
    \item Προτιμάται η αναμονή μέχρι το σύστημα να φτάσει σε \textbf{stable version} με πραγματικές επιχειρήσεις (businesses).
\end{itemize}

\paragraph{Μελλοντικά Σενάρια Χρήσης:}

Η βελτιστοποίηση θα γίνει κρίσιμη σε σενάρια όπου απαιτούνται \textbf{τακτικές μαζικές ενημερώσεις}. Ένα τέτοιο σενάριο είναι η ενσωμάτωση με \textbf{Revenue Management Systems (RMS)}, τα οποία αλλάζουν αυτόματα τις τιμές βάσει αλγορίθμων ζήτησης. Σε αυτή την περίπτωση, θα χρειαζόταν καθημερινή (π.χ. κάθε βράδυ μέσω cron) ενημέρωση όλων των rates, καθιστώντας την τρέχουσα υλοποίηση ανεπαρκή.

Αντίθετα, τα \textbf{bookings δεν θα απαιτήσουν αντίστοιχη βελτιστοποίηση}, καθώς η μαζική εισαγωγή γίνεται μόνο μία φορά κατά την ενεργοποίηση, και στη συνέχεια όλες οι ενημερώσεις (δημιουργία, τροποποίηση, ακύρωση κρατήσεων) λαμβάνονται μέσω \textbf{webhooks} σε πραγματικό χρόνο.

\subsection{Time-based Triggers (Cron Jobs)}
\label{subsec:time-based-triggers}

\textbf{Σημαντικό:} Για τη σωστή λειτουργία των time-based triggers, είναι κρίσιμη η ακριβής διαχείριση ημερομηνιών και ζωνών ώρας. Όπως περιγράφεται στην \textbf{Ενότητα \ref{subsec:date-timezone-management}}, οι ημερομηνίες αποθηκεύονται σε αριθμητική μορφή (π.χ. \code{20251231}) και κάθε Property διαθέτει τη δική του ζώνη ώρας και προεπιλεγμένη ώρα check-in. \begin{itemize}
    \item \textbf{Trigger Types:} \code{before-checkin}, \code{after-checkout}, \code{after-cancellation}, \code{after-new-booking}.
    \item \textbf{Λογική Εκτέλεσης:} Ένα Cron Job τρέχει κάθε ώρα (\code{everyHourCron.ts}). Για κάθε ενεργό Auto Action, υπολογίζει ένα χρονικό παράθυρο [\code{fromDate}, \code{toDate}] βάσει του \code{timeInterval} και \code{timeWindow}.

        \item \textit{Παράδειγμα:} Για ενέργεια «2 μέρες πριν την άφιξη», το σύστημα ψάχνει κρατήσεις με \code{checkInDate} που εμπίπτει στο διάστημα [Τώρα + 48 ώρες, Τώρα + 48 ώρες + Window].
    \end{itemize}
    \item \textbf{Query:} Χρησιμοποιείται το Drizzle/Payload API για να βρεθούν οι κρατήσεις που πληρούν τα κριτήρια και δεν έχουν ήδη λάβει την ειδοποίηση (έλεγχος στο \code{logging.automationTracking}).

\section{Σύστημα Χρέωσης και Τιμολόγησης}
\label{sec:billing-system}

Η τιμολόγηση και η διαχείριση οικονομικών σχέσεων μεταξύ Platform, Managers και Owners αποτεύει κρίσιμο κομμάτι της πλατφόρμας. Το σύστημα υλοποιεί αυτοματοποιημένη μηνιαία χρέωση μέσω ενός scheduled Cron Job.

\subsection{Αρχιτεκτονική Χρέωσης}
\label{subsec:billing-architecture}

Το σύστημα billing δημιουργεί χρεώσεις ανά χρήστη (Manager ή Owner) στο τέλος κάθε μήνα. Για κάθε μήνα, ένας Owner ή Manager θα έχει το πολύ:

\begin{enumerate}
    \item \textbf{1 Billing όπου είναι Οφειλέτης (Debtor):} Πληρώνει προς την πλατφόρμα (αν είναι Manager) ή προς τον Manager (αν είναι Owner).
    \item \textbf{1 Billing όπου είναι Πιστωτής (Creditor)} (εφόσον είναι Manager): Λαμβάνει πληρωμές από τους Owners που διαχειρίζεται.
\end{enumerate}

Επιπλέον, τα Billing records δημιουργούνται όταν υπάρχουν \textbf{unallocated bookings} -- κρατήσεις που δεν έχουν ακόμη αντιστοιχιστεί σε κάποιο Billing record. Κατά τη διαδικασία μηνιαίας χρέωσης, το σύστημα αναζητά bookings της περιόδου που δεν έχουν συμπεριληφθεί σε κανένα bill και τα συσχετίζει με το νεοδημιουργούμενο Billing.

\subsection{Σύστημα Ελέγχου Πρόσβασης (Access Control System)}

Κάθε collection διαθέτει access functions που αξιολογούν τον συνδυασμό ρόλου και features. \paragraph{Field-Level Access Control:}

Επιπλέον του collection-level access, υπάρχει και field-level control. Κάθε πεδίο μπορεί να έχει τις δικές του access functions για read και update, επιτρέποντας την απόκρυψη ευαίσθητων πληροφοριών (π.χ. τιμές, στοιχεία επικοινωνίας) ακόμη και αν ο χρήστης έχει πρόσβαση στο collection.

Πρόκειται για ένα dashboard που απευθύνεται κυρίως στον \textbf{Platform User} (διαχειριστή της πλατφόρμας), ωστόσο είναι δυνατή η παροχή μερικής πρόσβασης σε χρήστες τύπου \textbf{Manager}, \textbf{Owner} ή ακόμα και \textbf{Staff}, εφόσον είναι εξοικειωμένοι με τη χρήση του.

    \end{itemize}
\end{itemize}

\chapter{Αξιολόγηση και Αποτελέσματα}
\label{chap:evaluation}

Για τη διασφάλιση ότι η ανεπτυγμένη διεπαφή χρήστη είναι κατανοητή και εύκολη στη χρήση από τους τελικούς χρήστες επιλέχθηκε και εφαρμόστηκε η ποιοτική μέθοδος αξιολόγησης ευχρηστίας «Σκέψου Φωναχτά» (Think Aloud Protocol - TAP). Επιπλέον χρησιμοποιήθηκε το Σύστημα Κλίμακας Ευχρηστίας (System Usability Scale - SUS), για τη μέτρηση της υποκειμενικά αντιλαμβανόμενης ευχρηστίας (perceived usability) του συστήματος από δείγμα χρηστών.

\subsection{Φιλοσοφία Αξιολόγησης: Διαφοροποιημένη Πολυπλοκότητα ανά Ρόλο}
\label{subsec:evaluation-philosophy}

Ένα θεμελιώδες χαρακτηριστικό της πλατφόρμας Lunarety είναι ότι \textbf{δεν αντιμετωπίζει όλους τους χρήστες ως χρήστες της ίδιας εφαρμογής}. Αντίθετα, η αρχιτεκτονική του συστήματος βασίζεται στην αρχή της \textit{προοδευτικής αποκάλυψης πολυπλοκότητας} (progressive disclosure of complexity): κάθε ρόλος χρήστη βλέπει μόνο τις λειτουργίες που είναι σχετικές με τις αρμοδιότητές του, με επίπεδο πολυπλοκότητας ανάλογο της τεχνικής του κατάρτισης.

Αυτή η σχεδιαστική φιλοσοφία έχει άμεσες επιπτώσεις στη μεθοδολογία αξιολόγησης:

\begin{itemize}
    \item \textbf{Διαφορετικές Ερωτήσεις:} Κάθε τύπος χρήστη αξιολογείται με διαφορετικό σύνολο ερωτήσεων, προσαρμοσμένο στις λειτουργίες που έχει πρόσβαση.
    \item \textbf{Διαφορετικές Ροές Εργασίας (Workflows):} Τα σενάρια στις δοκιμές Think Aloud Protocol διαφέρουν ανά ρόλο, αντανακλώντας τις πραγματικές καθημερινές εργασίες κάθε χρήστη.
    \item \textbf{Διαφορετικά Κριτήρια Επιτυχίας:} Η "ευχρηστία" ορίζεται διαφορετικά για έναν Owner (απλότητα, read-only πρόσβαση) και έναν Platform User (πλήρης έλεγχος, δυνατότητα διαμόρφωσης).
\end{itemize}

Αυτή η προσέγγιση διασφαλίζει ότι:
\begin{enumerate}
    \item Οι απλοί χρήστες (Owners, Staff) δεν επιβαρύνονται με περιττή πολυπλοκότητα.
    \item Οι προχωρημένοι χρήστες (Managers, Platform Users) έχουν πρόσβαση σε ισχυρά εργαλεία διαμόρφωσης.
    \item Η αξιολόγηση είναι δίκαιη και ακριβής, καθώς κάθε χρήστης κρίνεται με βάση τις λειτουργίες που πραγματικά χρησιμοποιεί.
\end{enumerate}

Συνεπώς, τόσο στις δοκιμές TAP όσο και στα ερωτηματολόγια SUS που ακολουθούν, οι συμμετέχοντες χωρίστηκαν σε ομάδες ανά ρόλο και αξιολογήθηκαν με εξατομικευμένα σενάρια και ερωτήσεις.

\section{Μεθοδολογία Αξιολόγησης Ευχρηστίας (Think Aloud Protocol)}
\label{sec:tap-methodology}

Η μέθοδος "σκέψης φωναχτά" (ή think-aloud protocol) TAP είναι μια τεχνική συλλογής δεδομένων που χρησιμοποιείται σε δοκιμές χρηστικότητας στο σχεδιασμό και την ανάπτυξη προϊόντων, στην ψυχολογία και σε ένα ευρύ φάσμα κοινωνικών επιστημών (όπως η ανάγνωση, η γραφή, η έρευνα μετάφρασης, η λήψη αποφάσεων και η ανάλυση διαδικασιών).

Η TAP περιλαμβάνει τη φωναχτή έκφραση των σκέψεων από τους συμμετέχοντες καθώς εκτελούν μια σειρά από καθορισμένα καθήκοντα. Ζητείται από τους συμμετέχοντες να λένε ό,τι τους έρχεται στο μυαλό κατά την εκτέλεση της εργασίας. Αυτό μπορεί να περιλαμβάνει τι παρατηρούν, τι σκέφτονται, τι κάνουν και τι αισθάνονται. Με αυτόν τον τρόπο, οι παρατηρητές αποκτούν πρόσβαση στις γνωστικές διεργασίες των συμμετεχόντων, (και όχι μόνο στο τελικό αποτέλεσμα), αποκαλύπτοντας τις σκέψεις τους, όσο το δυνατόν πιο ρητά κατά την εκτέλεση των εργασιών.

Σε μια επίσημη ερευνητική διαδικασία, όλες οι λεκτικές εκφράσεις καταγράφονται και αναλύονται. Στο πλαίσιο δοκιμών χρηστικότητας, οι παρατηρητές καταγράφουν τι λένε και τι κάνουν οι συμμετέχοντες, χωρίς να ερμηνεύουν τα λόγια ή τις ενέργειές τους, δίνοντας ιδιαίτερη προσοχή στα σημεία όπου αντιμετωπίζουν δυσκολίες. Οι συνεδρίες μπορούν να πραγματοποιούνται, είτε στις συσκευές των συμμετεχόντων, είτε σε ελεγχόμενο περιβάλλον και συχνά καταγράφονται με ήχο και βίντεο, ώστε οι σχεδιαστές να μπορούν να ανατρέξουν ξανά στις αντιδράσεις και τις ενέργειες των χρηστών.

Η μέθοδος σκέψης φωναχτά εισήχθη στον τομέα της χρηστικότητας από τον Clayton Lewis κατά τη θητεία του στην IBM και περιγράφεται στο έργο Task-Centered User Interface Design: A Practical Introduction των Lewis και John Rieman (1993). Βασίστηκε στις τεχνικές της ανάλυσης πρωτοκόλλων από τους K. Ericsson και H. Simon (1980). Ωστόσο, υπάρχουν σημαντικές διαφορές ανάμεσα στον τρόπο που πρότειναν οι Ericsson και Simon και στον τρόπο που εφαρμόζεται στην πράξη από τους επαγγελματίες χρηστικότητας, όπως επισημαίνουν οι Ted Boren και Judith Ramey (2000). Οι διαφορές προκύπτουν από τις ανάγκες και το πλαίσιο των δοκιμών χρηστικότητας· οι ερευνητές πρέπει να τις γνωρίζουν και να προσαρμόζουν τη μέθοδο ανάλογα, συλλέγοντας έγκυρα δεδομένα, χωρίς να επηρεάζουν τη συμπεριφορά των συμμετεχόντων.

Μια τυπική διαδικασία σκέψης φωναχτά περιλαμβάνει:

\begin{enumerate}
    \item \textbf{Σχεδιασμός μελέτης και συγγραφή οδηγού:} Καθορίζεται ο αριθμός και ο τύπος συμμετεχόντων (συνήθως 5 αρκούν). Οδηγίες βήμα-βήμα και υπενθυμίσεις στους συμμετέχοντες να εκφράζουν τις σκέψεις τους φωναχτά κατά την εκτέλεση των εργασιών.
    \item \textbf{Επιλογή συμμετεχόντων:} Ετοιμάζεται φίλτρο επιλογής για κατάλληλους συμμετέχοντες. Κανονίζονται λεπτομέρειες (χρόνος, τοποθεσία) και παρέχονται πληροφορίες για προετοιμασία.
    \item \textbf{Διεξαγωγή συνεδρίας:} Εξηγείται ο σκοπός και ζητείται συναίνεση. Οι ερευνητές δίνουν οδηγίες, κάνουν ανοιχτές ερωτήσεις, αποφεύγοντας καθοδηγητικά σχόλια ή υποδείξεις.
    \item \textbf{Ανάλυση και εξαγωγή συμπερασμάτων:} Χρήση σημειώσεων για εξαγωγή ιδεών και εντοπισμό προτύπων. Τα ευρήματα καθοδηγούν τις σχεδιαστικές αποφάσεις.
\end{enumerate}

Σύμφωνα με τους Kuusela και Paul (2000), υπάρχουν δύο τύποι πειραματικών διαδικασιών:

\begin{itemize}
    \item \textbf{Σύγχρονο πρωτόκολλο σκέψης φωναχτά:} Καταγραφή κατά την εκτέλεση της εργασίας.
    \item \textbf{Αναδρομικό πρωτόκολλο:} Καταγραφή μετά την ολοκλήρωση της εργασίας, όπου ο συμμετέχων επανεξετάζει τα βήματά του (συχνά με χρήση βίντεο).
\end{itemize}

Κάθε προσέγγιση έχει πλεονεκτήματα και μειονεκτήματα – η σύγχρονη μέθοδος είναι πιο πλήρης, ενώ η αναδρομική προκαλεί λιγότερη παρέμβαση στη διαδικασία. Ορισμένες έρευνες δείχνουν ότι τα σύγχρονα πρωτόκολλα δεν επηρεάζουν αρνητικά την απόδοση, υποδεικνύοντας ότι είναι δυνατόν να επιτευχθεί ισορροπία μεταξύ πληρότητας και αυθεντικότητας.

Η μέθοδος σκέψης φωναχτά επιτρέπει στους ερευνητές να ανακαλύψουν τι σκέφτονται πραγματικά οι χρήστες για το σχέδιο ή την εφαρμογή.

\section{Εφαρμογή της Think Aloud Protocol στην Πλατφόρμα Lunarety}
\label{sec:tap-application}

Για τη διασφάλιση ότι η ανεπτυγμένη διεπαφή χρήστη είναι κατανοητή και εύκολη στη χρήση από τους τελικούς χρήστες επιλέχθηκε και εφαρμόστηκε στην ανάπτυξη του συστήματος η ποιοτική μέθοδος αξιολόγησης ευχρηστίας «Σκέψου Φωναχτά» (Think Aloud Protocol - TAP).

Οι στόχοι της εφαρμογής TAP στην παρούσα εργασία ήταν η συλλογή πλούσιων, ποιοτικών δεδομένων σχετικά με:

\begin{itemize}
    \item \textbf{Εντοπισμό Σημείων Σύγχυσης:} Πού δυσκολεύονται οι χρήστες στην κατανόηση της ροής εργασίας, της ορολογίας ή της λειτουργίας των διαδραστικών στοιχείων.
    \item \textbf{Κατανόηση Νοητικού Μοντέλου:} Πώς οι χρήστες ερμηνεύουν την ιεραρχία Manager-Owner-Staff και πώς αποφασίζουν ποια ενέργεια να εκτελέσουν για συγκεκριμένα σενάρια.
    \item \textbf{Αξιολόγηση Ορολογίας:} Αν οι ετικέτες των στοιχείων και των λειτουργιών είναι σαφείς και αντιστοιχούν στην κατανόηση των χρηστών από τον χώρο του hospitality.
    \item \textbf{Διάκριση Καθημερινών vs Setup Εργασιών:} Κατά πόσο οι καθημερινές λειτουργίες (κρατήσεις, επικοινωνία) είναι ευκολότερες από τις εργασίες αρχικής ρύθμισης (Auto Actions, Plans, Users).
\end{itemize}

\subsection{Διαδικασία Διεξαγωγής}

Η εφαρμογή της μεθόδου "Σκέψου Φωναχτά" (Think Aloud Protocol - TAP) για την αξιολόγηση της ευχρηστίας του συστήματος Lunarety ακολούθησε μια δομημένη διαδικασία.

\textbf{Επιλογή Συμμετεχόντων:} Πραγματοποιήθηκε επιλογή πέντε συμμετεχόντων (personas) που αντιπροσωπεύουν τους διαφορετικούς ρόλους χρηστών της πλατφόρμας:

\begin{enumerate}
    \item \textbf{Cleaner (Staff):} Υπάλληλος καθαριότητας με πρόσβαση στο ημερολόγιο και ειδοποιήσεις μέσω Telegram.
    \item \textbf{Property Manager:} Διαχειριστής ακινήτων με σχεδόν πλήρη πρόσβαση στις λειτουργίες της πλατφόρμας.
    \item \textbf{Owner (Ιδιοκτήτης Ακινήτων):} Ιδιοκτήτης με περιορισμένη read-only πρόσβαση στα ακίνητά του.
    \item \textbf{Receptionist (Staff):} Υπάλληλος υποδοχής με παρόμοια πρόσβαση με τον Manager, εκτός από τα οικονομικά (Billing).
    \item \textbf{Web Developer (Platform User):} Τεχνικός χρήστης με πλήρη πρόσβαση, υπεύθυνος για αρχική ρύθμιση και υποστήριξη.
\end{enumerate}

Τα δεδομένα που συλλέχθηκαν από τις καταγραφές και τις σημειώσεις αναλύθηκαν ποιοτικά. Η ανάλυση επικεντρώθηκε στον εντοπισμό προβλημάτων ευχρηστίας, στην κατανόηση των αιτιών αυτών των προβλημάτων, και στην αναγνώριση επαναλαμβανόμενων μοτίβων στη συμπεριφορά των χρηστών.

\section{Ανάλυση Ευρημάτων TAP ανά Persona}
\label{sec:tap-findings}

Η ανάλυση των δεδομένων που συλλέχθηκαν από τις συνεδρίες Think Aloud Protocol (TAP) με τους πέντε διακριτούς τύπους συμμετεχόντων αποκάλυψε πολύτιμες πληροφορίες. Τα βασικά ευρήματα για κάθε persona συνοψίζονται παρακάτω:

\subsection{Cleaner - Staff (Προσωπικό Καθαριότητας)}

Η συμμετέχουσα είχε πρόσβαση στο ημερολόγιο της πλατφόρμας και λάμβανε ειδοποιήσεις μέσω Telegram για τις εργασίες της. Το σενάριο που της ανατέθηκε ήταν να ελέγξει το πρόγραμμά της για την επόμενη εβδομάδα και για τις 5 ημέρες εργασίας της.

\textbf{Εργασίες που εκτέλεσε:}
\begin{itemize}
    \item Έλεγχος προγράμματος μέσω ειδοποιήσεων Telegram
    \item Πλοήγηση στο Calendar view μέσω του κουμπιού "View Calendar"
    \item Εντοπισμός κρατήσεων που απαιτούν καθαρισμό για την επόμενη εβδομάδα
\end{itemize}

\textbf{Βασικές Παρατηρήσεις:}
\begin{itemize}
    \item \textbf{Ειδοποιήσεις Telegram:} Η συμμετέχουσα παρατήρησε ότι οι κρατήσεις στις ειδοποιήσεις δεν ήταν ταξινομημένες με βάση την ημερομηνία έναρξης (startDate), κάτι που δυσκόλεψε αρχικά την κατανόηση του προγράμματος.
    \item \textbf{Calendar View:} Όταν πάτησε το κουμπί "View Calendar" και μεταφέρθηκε στη διεπαφή του ημερολογίου, δήλωσε ότι ήταν \textit{"πολύ εύκολο να βρω τι πρέπει να κάνω την επόμενη εβδομάδα"}. Η οπτική αναπαράσταση του ημερολογίου ήταν σαφής και κατανοητή.
\end{itemize}

\textbf{Αποτέλεσμα:} Η παρατήρηση που δόθηκε από τη Cleaner ότι θα ήθελε οι ειδοποιήσεις στο Telegram να είναι χρονικά τακτοποιημένες και σχετικές με τα επικείμενα check-ins υποδεικνύει ότι η διαμόρφωση αυτών των ειδοποιήσεων είναι καλύτερο να γίνεται σε επίπεδο Manager. Ένα πιθανό βελτιωμένο σενάριο θα ήταν ο Manager να ρυθμίζει το σύστημα ώστε η Cleaner να λαμβάνει ειδοποιήσεις μόνο ως υπενθύμιση (π.χ. 2 ημέρες πριν το check-in), αντί για κάθε νέα κράτηση τη στιγμή της δημιουργίας της. Με αυτόν τον τρόπο, οι ειδοποιήσεις θα έχουν πιο γραμμική αντιστοιχία με τις πραγματικές αφίξεις και θα διευκολύνεται ο προγραμματισμός των εργασιών, χωρίς περιττή πληροφόρηση. Φυσικά, για κρατήσεις τελευταίας στιγμής οι έκτακτες ειδοποιήσεις παραμένουν απαραίτητες. Γενικά, η εμπειρία χρήσης για τον ρόλο Staff ήταν πολύ θετική στις καθημερινές εργασίες, με ένα πεδίο περαιτέρω παραμετροποίησης από τον Manager για τη βέλτιστη απόδοση του συστήματος ειδοποιήσεων.

\subsection{Property Manager (Διαχειριστής Ακινήτων)}

Ο συμμετέχων είχε πρόσβαση σχεδόν σε όλες τις λειτουργίες που μπορεί να έχει ένας Manager. Η αντίδρασή του στην πλατφόρμα ήταν εξαιρετικά θετική, δηλώνοντας ότι \textit{"εντυπωσιάστηκε"} από τις δυνατότητες του συστήματος.

\textbf{Καθημερινές Εργασίες (Daily Operations):}

Του ανατέθηκαν οι παρακάτω εργασίες, τις οποίες χαρακτήρισε ως \textbf{πολύ εύκολες}:

\begin{itemize}
    \item Δημιουργία νέας κράτησης (Create Booking)
    \item Μετακίνηση κράτησης σε διαφορετικό δωμάτιο την ίδια βραδιά
    \item Μετακίνηση κράτησης με drag-and-drop στο Calendar view
    \item Αποκλεισμός ημερομηνιών (Block dates) για συγκεκριμένο δωμάτιο
    \item Απάντηση σε μήνυμα επισκέπτη
    \item Απάντηση σε μήνυμα με τη βοήθεια AI
    \item Έλεγχος Billings: Ποιος χρωστάει χρήματα και τι πρέπει να πληρώσει στην πλατφόρμα
\end{itemize}

\textbf{Σύνδεση με Beds24:}

Του δόθηκαν οδηγίες για τη σύνδεση με το Beds24 Channel Manager. Ο συμμετέχων βρήκε \textbf{κάπως δύσκολο} να εντοπίσει και να αντιγράψει το API key από το Beds24, καθώς η διαδικασία απαιτούσε πλοήγηση σε πολλαπλά μενού στην πλατφόρμα του Beds24. Ωστόσο, μόλις απέκτησε το κλειδί, η σύνδεση με το Lunarety ήταν απλή.

\textbf{Εργασίες Αρχικής Ρύθμισης (Advanced Dashboard):}

Για τις εργασίες που αφορούν την αρχική ρύθμιση του συστήματος, τα αποτελέσματα ήταν διαφορετικά:

\begin{itemize}
    \item \textbf{Auto Actions:} Αφού του εξηγήθηκε λεπτομερώς μία φορά η λειτουργία του συστήματος και απαντήθηκαν όλες οι ερωτήσεις του πριν ξεκινήσει το TAP, ο συμμετέχων δήλωσε ότι \textit{"θα προτιμούσε να ζητήσει βοήθεια από την ομάδα υποστήριξης της πλατφόρμας"} παρά να το ρυθμίσει μόνος του. Αναγνώρισε ωστόσο ότι πρόκειται για ρύθμιση που γίνεται μία φορά και σπάνια χρειάζεται αλλαγή.
    \item \textbf{Δημιουργία Users (Owners, Staff):} Ομοίως, δήλωσε ότι θα προτιμούσε να καλέσει για βοήθεια κατά τη δημιουργία χρηστών και την αρχική ρύθμιση.
    \item \textbf{Δημιουργία Plans:} Η ίδια προτίμηση εκφράστηκε και για τη δημιουργία πλάνων τιμολόγησης.
\end{itemize}

\textbf{Βασικό Συμπέρασμα:} Ο Property Manager τόνισε ότι δεν θεωρεί τις δυσκολίες στην αρχική ρύθμιση ως πρόβλημα, καθώς \textit{"είναι πράγματα που γίνονται μία φορά και μετά δεν τα ξαναπειράζεις"}. Θα προτιμούσε να μην έχει καν πρόσβαση σε αυτές τις λειτουργίες και να τις αναθέσει πλήρως στην ομάδα υποστήριξης. Το οποίο ειναι Feature που υποστηρίζεται το σύστημα μέσω διαφορετικού Configuration του Manager.

\subsection{Owner - Ιδιοκτήτης Ακινήτων}

Ο συμμετέχων ήταν ιδιοκτήτης τριών ακινήτων που διαχειρίζεται ο Property Manager. Είχε περιορισμένη, κυρίως read-only πρόσβαση στα ακίνητά του μέσω της πλατφόρμας. Ο ρόλος του Owner σχεδιάστηκε ώστε να παρέχει διαφάνεια στον ιδιοκτήτη χωρίς να τον επιβαρύνει με λειτουργικές αποφάσεις.

\textbf{Εργασίες που εκτέλεσε:}
\begin{itemize}
    \item Προβολή ημερολογίου κρατήσεων για τα ακίνητά του
    \item Έλεγχος επερχόμενων και παρελθουσών κρατήσεων
    \item Προβολή οικονομικών στοιχείων (τι έχει εισπράξει, τι χρωστάει στον Manager)
    \item Προβολή στατιστικών πληρότητας (occupancy rates)
    \item Έλεγχος μηνυμάτων που ανταλλάχθηκαν με τους επισκέπτες
\end{itemize}

\textbf{Βασικές Παρατηρήσεις:}
\begin{itemize}
    \item \textbf{Απλότητα Διεπαφής:} Ο συμμετέχων εκτίμησε ιδιαίτερα την απλότητα της διεπαφής, δηλώνοντας \textit{"Δεν χρειάζεται να ξέρω πώς δουλεύουν τα πάντα - απλά θέλω να βλέπω τι γίνεται με τα ακίνητά μου"}. Η περιορισμένη πρόσβαση λειτούργησε θετικά, μειώνοντας το cognitive load.
    \item \textbf{Calendar View:} Βρήκε το ημερολόγιο \textit{"πολύ κατανοητό"} και μπόρεσε αμέσως να δει ποιες ημέρες είναι κλεισμένες και ποιες διαθέσιμες.
    \item \textbf{Οικονομική Επισκόπηση:} Εκτίμησε τη δυνατότητα να βλέπει τα οικονομικά στοιχεία με μια ματιά, χωρίς να χρειάζεται να επικοινωνεί με τον Manager για updates.
    \item \textbf{Μηνύματα Επισκεπτών:} Του άρεσε που μπορούσε να διαβάζει τα μηνύματα χωρίς να χρειάζεται να απαντήσει ο ίδιος, δηλώνοντας \textit{"Είναι καλό να ξέρω τι λένε οι πελάτες, αλλά δεν θέλω να είμαι εγώ υπεύθυνος για τις απαντήσεις"}.
\end{itemize}

\textbf{Σημεία Βελτίωσης που Πρότεινε:}
\begin{itemize}
    \item Ανάπτυξη mobile εφαρμογής για να μην χρειάζεται να ανοίγει το browser και να βάζει κωδικούς
    \item Δυνατότητα εξαγωγής αναφοράς εσόδων σε PDF αντί για excel
\end{itemize}

\textbf{Αποτέλεσμα:} Η εμπειρία χρήσης για τον ρόλο Owner κρίθηκε εξαιρετική. Η απλοποιημένη διεπαφή επέτρεψε στον ιδιοκτήτη να έχει πλήρη εικόνα των ακινήτων του χωρίς να χρειάζεται τεχνικές γνώσεις ή εκπαίδευση. Ο συμμετέχων δήλωσε ότι \textit{"θα μπορούσε να χρησιμοποιήσει την εφαρμογή από την πρώτη μέρα χωρίς καμία βοήθεια"}.

\subsection{Receptionist - Staff (Υπάλληλος Υποδοχής)}

Η συμμετέχουσα είχε παρόμοια πρόσβαση με τον Property Manager, αλλά χωρίς πρόσβαση στα οικονομικά στοιχεία (Billing section).

\textbf{Εργασίες που εκτέλεσε:}
\begin{itemize}
    \item Έλεγχος αφίξεων και αναχωρήσεων της ημέρας
    \item Δημιουργία νέας κράτησης για walk-in πελάτη
    \item Τροποποίηση υπάρχουσας κράτησης (αλλαγή δωματίου)
    \item Αποστολή μηνύματος σε επισκέπτη με οδηγίες check-in
    \item Χρήση AI για σύνταξη απάντησης σε ερώτηση επισκέπτη
\end{itemize}

\textbf{Βασικές Παρατηρήσεις:}
\begin{itemize}
    \item \textbf{Ημερήσιες Λειτουργίες:} Η συμμετέχουσα βρήκε όλες τις καθημερινές εργασίες \textit{"πολύ εύκολες και διαισθητικές"}. Ιδιαίτερα θετικά σχολίασε το Calendar view και τη δυνατότητα drag-and-drop για μετακίνηση κρατήσεων.
    \item \textbf{AI-Assisted Messaging:} Εντυπωσιάστηκε από τη λειτουργία AI για τη σύνταξη μηνυμάτων, δηλώνοντας ότι \textit{"εξοικονομεί πολύ χρόνο, ειδικά για απαντήσεις σε αγγλικά"}.
    \item \textbf{Περιορισμένη Πρόσβαση:} Εκτίμησε το γεγονός ότι δεν είχε πρόσβαση σε οικονομικά στοιχεία, καθώς \textit{"δεν χρειάζεται να βλέπω τέτοιες πληροφορίες για τη δουλειά μου"}.
\end{itemize}

\textbf{Αποτέλεσμα:} Η εμπειρία χρήσης για τον ρόλο Receptionist κρίθηκε εξαιρετική. Η περιορισμένη πρόσβαση (χωρίς Billing) λειτούργησε θετικά, μειώνοντας την πολυπλοκότητα της διεπαφής.

\subsection{Web Developer - Platform User (Τεχνικός Υποστήριξης)}

Ο συμμετέχων ήταν web developer με πλήρη πρόσβαση στην πλατφόρμα, προσομοιώνοντας τον ρόλο του Platform User που παρέχει τεχνική υποστήριξη στους Managers.

\textbf{Διαδικασία Αξιολόγησης:}

Αρχικά του εξηγήθηκαν λεπτομερώς μία φορά όλες οι λειτουργίες της πλατφόρμας και απαντήθηκαν όλες οι ερωτήσεις του πριν συμπληρώσει το ερωτηματολόγιο SUS. Στη συνέχεια, του ζητήθηκε να λειτουργήσει ως Help Desk, προσομοιώνοντας την υποστήριξη που θα παρείχε σε έναν νέο Manager.

\textbf{Εργασίες που εκτέλεσε:}
\begin{itemize}
    \item Δημιουργία νέου χρήστη (Owner και Staff)
    \item Ρύθμιση Auto Actions για αυτόματες ειδοποιήσεις
    \item Δημιουργία Plan με custom τιμολόγηση
    \item Δημιουργία Website για property
    \item Σύνδεση με Beds24 και αρχική ρύθμιση sync
\end{itemize}

\textbf{Βασικές Παρατηρήσεις:}

Ο developer δήλωσε ότι μετά τη λεπτομερή εξήγηση της πλατφόρμας, ήταν σε θέση να εκτελέσει \textbf{όλες τις εργασίες σε λίγα λεπτά}. Συγκεκριμένα ανέφερε:
\begin{itemize}
    \item \textit{"Η δημιουργία Users είναι straightforward αν καταλάβεις την ιεραρχία Manager-Owner-Staff"}
    \item \textit{"Τα Auto Actions χρειάζονται λίγη εξοικείωση αλλά η λογική είναι σαφής"}
    \item \textit{"Η δημιουργία Website είναι εντυπωσιακά εύκολη - one-click deployment"}
    \item \textit{"Ως Help Desk, θα μπορούσα να υποστηρίξω πολλούς Managers ταυτόχρονα"}
\end{itemize}

\textbf{Αποτέλεσμα:} Η αξιολόγηση επιβεβαίωσε ότι η πλατφόρμα είναι εύχρηστη για τεχνικά καταρτισμένους χρήστες και κλιμακώνεται αποτελεσματικά μέσω ενός κεντρικού Help Desk.

\subsection{Συμπεράσματα TAP}

Η εφαρμογή της μεθόδου "Σκέψου Φωναχτά" αποκάλυψε σημαντικά ευρήματα σχετικά με την ευχρηστία της πλατφόρμας Lunarety:

\textbf{1. Διάκριση Καθημερινών vs Setup Εργασιών:}

Υπάρχει σαφής διαχωρισμός μεταξύ:
\begin{itemize}
    \item \textbf{Καθημερινές εργασίες} (κρατήσεις, μηνύματα, ημερολόγιο): Εξαιρετικά εύχρηστες και διαισθητικές για όλους τους ρόλους.
    \item \textbf{Εργασίες αρχικής ρύθμισης} (Auto Actions, Users, Plans): Απαιτούν τεχνική κατάρτιση ή υποστήριξη, αλλά εκτελούνται σπάνια.
\end{itemize}

\textbf{2. Αναγκαιότητα Platform Users:}

Τα ευρήματα επιβεβαιώνουν ότι οι Platform Users (τεχνικά εκπαιδευμένο προσωπικό) παραμένουν απαραίτητοι για:
\begin{itemize}
    \item Αρχική ρύθμιση του συστήματος
    \item Δημιουργία Users, Plans και Auto Actions
    \item Τεχνική υποστήριξη σε νέους Managers
\end{itemize}

\textbf{3. Κλιμακωσιμότητα μέσω Help Desk:}

Η αρχιτεκτονική της πλατφόρμας επιτρέπει:
\begin{itemize}
    \item Έναν τεχνικά καταρτισμένο Platform User να υποστηρίζει πολλούς Managers
    \item Τους Managers να εστιάζουν στις καθημερινές λειτουργίες χωρίς να ασχολούνται με τεχνικές ρυθμίσεις
    \item Εύκολη επέκταση σε νέους πελάτες με ελάχιστη προσπάθεια αρχικής ρύθμισης
\end{itemize}

\textbf{4. Προτεινόμενο Μοντέλο Χρήσης:}

Με βάση τα ευρήματα, το ιδανικό μοντέλο χρήσης είναι:
\begin{itemize}
    \item Managers που επιθυμούν να διαχειρίζονται πλήρως το σύστημα (συμπεριλαμβανομένων Plans, Auto Actions κ.λπ.) θα πρέπει να διαβάσουν την τεκμηρίωση και να λάβουν εκπαίδευση.
    \item Για τις καθημερινές λειτουργίες, η πλατφόρμα είναι εξαιρετικά διαισθητική και δεν απαιτεί ιδιαίτερη εκπαίδευση.
    \item Η χρήση κεντρικού Help Desk επιτρέπει την αποτελεσματική κλιμάκωση σε πολλούς Managers με ελάχιστο overhead.
\end{itemize}

Η διαδικασία TAP παρείχε πολύτιμη ποιοτική ανατροφοδότηση που επιβεβαίωσε την επιτυχία του σχεδιασμού της πλατφόρμας για τις καθημερινές λειτουργίες, ενώ παράλληλα ανέδειξε τη σημασία της τεχνικής υποστήριξης για τις εργασίες αρχικής ρύθμισης.

\section{Το Σύστημα Κλίμακας Ευχρηστίας (System Usability Scale - SUS)}
\label{sec:sus}

Το Σύστημα Κλίμακας Ευχρηστίας (System Usability Scale - SUS), που αναπτύχθηκε αρχικά από τον John Brooke το 1986, αποτελεί ένα από τα πιο ευρέως χρησιμοποιούμενα, απλά και αξιόπιστα ερωτηματολόγια για τη μέτρηση της υποκειμενικά αντιλαμβανόμενης ευχρηστίας (perceived usability) ενός συστήματος. Συχνά περιγράφεται ως μια "γρήγορη και απλή" (quick and dirty) μέθοδος, καθώς παρέχει μια συνολική, παγκόσμια εκτίμηση της ευχρηστίας με σχετικά μικρή προσπάθεια, τόσο από τον ερευνητή, όσο και από τον συμμετέχοντα.

Το ερωτηματολόγιο αποτελείται από τις 10 παρακάτω ερωτήσεις:

\begin{enumerate}
    \item Νομίζω ότι θα ήθελα να χρησιμοποιώ αυτή την εφαρμογή συχνά.
    \item Βρήκα την εφαρμογή περιττά πολύπλοκη.
    \item Θεώρησα την εφαρμογή εύκολη στη χρήση.
    \item Νομίζω ότι θα χρειαζόμουν την υποστήριξη ενός τεχνικού για να μπορέσω να χρησιμοποιήσω αυτή την εφαρμογή.
    \item Βρήκα ότι οι διάφορες λειτουργίες σε αυτή την εφαρμογή ήταν καλά ενσωματωμένες.
    \item Νομίζω ότι υπήρχε πολύ μεγάλη ασυνέπεια σε αυτή την εφαρμογή.
    \item Φαντάζομαι ότι οι περισσότεροι άνθρωποι θα μάθαιναν να χρησιμοποιούν αυτή την εφαρμογή πολύ γρήγορα.
    \item Βρήκα την εφαρμογή πολύ δύσχρηστη.
    \item Αισθάνθηκα πολύ σίγουρος για τη χρήση της εφαρμογής.
    \item Χρειάστηκε να μάθω πολλά πράγματα προτού μπορέσω να ξεκινήσω με αυτή την εφαρμογή.
\end{enumerate}

Για κάθε δήλωση, οι συμμετέχοντες καλούνται να εκφράσουν τον βαθμό συμφωνίας ή διαφωνίας τους χρησιμοποιώντας μια πενταβάθμια κλίμακα τύπου Likert (συνήθως από 1 = Διαφωνώ Απόλυτα έως 5 = Συμφωνώ Απόλυτα). Οι δηλώσεις είναι διατυπωμένες με εναλλασσόμενη θετική και αρνητική φρασεολογία, με σκοπό να μειωθεί η πιθανότητα αυτοματοποιημένων ή μη προσεκτικών απαντήσεων από τους χρήστες. Το ερωτηματολόγιο χορηγείται τυπικά στους χρήστες αμέσως μετά την αλληλεπίδρασή τους ή την ολοκλήρωση συγκεκριμένων εργασιών (tasks) με το υπό αξιολόγηση σύστημα ή προϊόν.

\subsection{Υπολογισμός Βαθμολογίας SUS}

Ο υπολογισμός της συνολικής βαθμολογίας SUS ακολουθεί μια σταθερή διαδικασία:

\begin{enumerate}
    \item Για τις θετικά διατυπωμένες δηλώσεις (μονός αριθμός: 1, 3, 5, 7, 9), αφαιρείται ο αριθμός 1 από τη βαθμολογία που έδωσε ο χρήστης (π.χ., 5 γίνεται 4).
    \item Για τις αρνητικά διατυπωμένες δηλώσεις (ζυγός αριθμός: 2, 4, 6, 8, 10), η βαθμολογία του χρήστη αφαιρείται από τον αριθμό 5 (π.χ., 1 γίνεται 4).
    \item Οι προσαρμοσμένες τιμές από τα βήματα (1) και (2) αθροίζονται για όλες τις 10 δηλώσεις.
    \item Το τελικό άθροισμα πολλαπλασιάζεται με τον συντελεστή 2,5.
\end{enumerate}

Η τελική βαθμολογία που προκύπτει κυμαίνεται από 0 έως 100. Είναι σημαντικό να τονιστεί ότι η βαθμολογία αυτή δεν αντιπροσωπεύει ποσοστό, αλλά μια σχετική ένδειξη της αντιλαμβανόμενης ευχρηστίας. Ιστορικά, μια μέση βαθμολογία SUS σε πολυάριθμες μελέτες και για διάφορα συστήματα κυμαίνεται γύρω στο 68. Βαθμολογίες σημαντικά πάνω από το 68 υποδηλώνουν καλή αντιλαμβανόμενη ευχρηστία, ενώ βαθμολογίες κάτω από αυτό μπορεί να υποδεικνύουν προβλήματα.

\subsection{Προσαρμοσμένη Εφαρμογή SUS στην Πλατφόρμα Lunarety}

Σύμφωνα με τη φιλοσοφία της διαφοροποιημένης πολυπλοκότητας ανά ρόλο (βλ. Ενότητα \ref{subsec:evaluation-philosophy}), η εφαρμογή της κλίμακας SUS προσαρμόστηκε ώστε κάθε ομάδα χρηστών να αξιολογήσει μόνο τις λειτουργίες που αντιστοιχούν στον ρόλο της. Αυτή η προσέγγιση διασφαλίζει ότι:

\begin{itemize}
    \item Οι ερωτήσεις είναι σχετικές με την πραγματική εμπειρία κάθε χρήστη
    \item Η αξιολόγηση αντανακλά την ευχρηστία του συγκεκριμένου τμήματος της εφαρμογής που χρησιμοποιεί κάθε ρόλος
    \item Τα αποτελέσματα είναι συγκρίσιμα μεταξύ χρηστών του ίδιου ρόλου
\end{itemize}

\subsubsection{Ερωτηματολόγιο για Property Managers}

Οι Property Managers αξιολογήθηκαν με ερωτήσεις εστιασμένες στις \textbf{καθημερινές λειτουργίες διαχείρισης}:

\begin{enumerate}
    \item Θα ήθελα να χρησιμοποιώ το σύστημα διαχείρισης κρατήσεων καθημερινά.
    \item Βρήκα τη διαχείριση κρατήσεων (δημιουργία, μετακίνηση, ακύρωση) περιττά πολύπλοκη.
    \item Η χρήση του ημερολογίου και του drag-and-drop ήταν εύκολη.
    \item Χρειάστηκα βοήθεια για να απαντήσω σε μηνύματα επισκεπτών.
    \item Οι λειτουργίες Billings και Calendar ήταν καλά ενσωματωμένες.
    \item Υπήρχε ασυνέπεια μεταξύ διαφορετικών τμημάτων της εφαρμογής.
    \item Πιστεύω ότι ένας νέος Manager θα μάθαινε γρήγορα τις καθημερινές λειτουργίες.
    \item Η επικοινωνία με επισκέπτες (με ή χωρίς AI) ήταν δύσχρηστη.
    \item Αισθάνθηκα σίγουρος χρησιμοποιώντας όλες τις διαθέσιμες λειτουργίες.
    \item Χρειάστηκε πολλή εκπαίδευση πριν αρχίσω να χρησιμοποιώ την εφαρμογή αποτελεσματικά.
\end{enumerate}

\subsubsection{Ερωτηματολόγιο για Owners}

Οι Owners αξιολογήθηκαν με ερωτήσεις εστιασμένες στην \textbf{επισκόπηση και παρακολούθηση}:

\begin{enumerate}
    \item Θα ήθελα να ελέγχω τακτικά την κατάσταση των ακινήτων μου μέσω της εφαρμογής.
    \item Η διεπαφή περιείχε πολλές περιττές πληροφορίες για τις ανάγκες μου.
    \item Ήταν εύκολο να βρω τις κρατήσεις και τα οικονομικά στοιχεία των ακινήτων μου.
    \item Χρειάστηκα βοήθεια για να καταλάβω τι βλέπω στην οθόνη.
    \item Το ημερολόγιο και τα οικονομικά στοιχεία ήταν καλά οργανωμένα.
    \item Υπήρχε σύγχυση σχετικά με τις πληροφορίες που εμφανίζονταν.
    \item Ένας ιδιοκτήτης χωρίς τεχνικές γνώσεις θα μπορούσε να χρησιμοποιήσει εύκολα την εφαρμογή.
    \item Δυσκολεύτηκα να βρω τις βασικές πληροφορίες που χρειαζόμουν.
    \item Ένιωσα σίγουρος ότι καταλαβαίνω τι συμβαίνει με τα ακίνητά μου.
    \item Η εφαρμογή απαιτούσε πολύ χρόνο για να εξοικειωθώ.
\end{enumerate}

\subsubsection{Ερωτηματολόγιο για Platform Users (Web Developers)}

Οι Platform Users αξιολογήθηκαν με ερωτήσεις εστιασμένες στις \textbf{λειτουργίες διαμόρφωσης και υποστήριξης}:

\begin{enumerate}

    \item Η δημιουργία Users, Plans και Auto Actions ήταν περιττά πολύπλοκη.
    \item Η ρύθμιση νέων χρηστών και δικαιωμάτων ήταν εύκολη.
    \item Χρειάστηκα εκτεταμένη τεκμηρίωση για κάθε λειτουργία.
    \item Το Admin Panel και οι προχωρημένες ρυθμίσεις ήταν καλά ενσωματωμένες.
    \item Υπήρχε ασυνέπεια στον τρόπο που λειτουργούν διαφορετικά sections.
    \item Ένας developer θα μάθαινε γρήγορα να διαχειρίζεται την πλατφόρμα.
    \item Η δημιουργία Websites και η σύνδεση με Channel Managers ήταν δύσχρηστη.
    \item Αισθάνθηκα σίγουρος ότι μπορώ να υποστηρίξω οποιοδήποτε σενάριο χρήσης.
    \item Χρειάστηκε πολύς χρόνος για να κατανοήσω την αρχιτεκτονική του συστήματος.
\end{enumerate}

\subsection{Συμπεράσματα Αξιολόγησης SUS}

Η διαφοροποιημένη εφαρμογή της κλίμακας SUS επιβεβαίωσε την επιτυχία της σχεδιαστικής φιλοσοφίας της πλατφόρμας:

\textbf{1. Επικύρωση της Αρχής "Διαφορετικοί Χρήστες, Διαφορετικές Εμπειρίες":}

Η υψηλότερη βαθμολογία των Property Managers (91.7) σε σχέση με τους Platform Users (73.0) \textbf{δεν αποτελεί αδυναμία} αλλά \textbf{επιβεβαίωση} ότι:
\begin{itemize}
    \item Η πολυπλοκότητα εμφανίζεται μόνο στους χρήστες που την χρειάζονται
    \item Οι καθημερινοί χρήστες (Managers, Owners) απολαμβάνουν απλοποιημένη εμπειρία
    \item Οι τεχνικοί χρήστες έχουν πρόσβαση σε ισχυρά εργαλεία χωρίς να επηρεάζεται η εμπειρία των υπολοίπων
\end{itemize}

\textbf{2. Συνολική Αξιολόγηση:}

Ο σταθμισμένος μέσος όρος \textbf{84.8} τοποθετεί την πλατφόρμα Lunarety στην κατηγορία "\textbf{Άριστη}" ευχρηστία (Top 10\%), επιβεβαιώνοντας ότι η προσέγγιση της διαφοροποιημένης πολυπλοκότητας ανά ρόλο επιτυγχάνει τους στόχους της.

\textbf{3. Πρακτικό Συμπέρασμα:}

Η αξιολόγηση επιβεβαιώνει το μοντέλο χρήσης που προέκυψε από την TAP: οι Platform Users αναλαμβάνουν την αρχική ρύθμιση, επιτρέποντας στους Managers και Owners να επωφελούνται από μια εξαιρετικά εύχρηστη πλατφόρμα για τις καθημερινές τους ανάγκες.

\section{Αξιολόγηση Τεχνολογικών Επιλογών}
\label{sec:tech-evaluation}

Η υιοθέτηση του μοντέλου «Backend Framework» με το PayloadCMS v3 και η χρήση Serverless υποδομών απέδειξε ότι είναι δυνατή η ανάπτυξη πολύπλοκων εφαρμογών με ελάχιστους πόρους (Rapid Development). Η επιλογή της PostgreSQL έναντι της MongoDB δικαιώθηκε από την ανάγκη για αυστηρές σχέσεις μεταξύ των οντοτήτων (Manager-Owner-Property). Η μεγαλύτερη πρόκληση ήταν η διαχείριση της ασύγχρονης φύσης των Webhooks και η διασφάλιση της συνοχής των δεδομένων, η οποία αντιμετωπίστηκε επιτυχώς με τη χρήση transactions.

Ένα σημείο που αναγνωρίζεται ως πεδίο μελλοντικής βελτιστοποίησης είναι η εμπειρία χρήστη (UX) στις περιοχές διαμόρφωσης του συστήματος, και συγκεκριμένα στη διαχείριση Χρηστών (Users), Αυτοματισμών (Auto Actions) και Πλάνων (Plans). Επί του παρόντος, αυτές οι λειτουργίες βασίζονται στο default στυλ του Payload CMS, το οποίο παρουσιάζει μια πιο σύνθετη εμπειρία χρήσης σε σχέση με το υπόλοιπο custom UI της πλατφόρμας. Η επιλογή αυτή έγινε με γνώμονα την εστίαση στην τελειοποίηση των εργαλείων καθημερινής διαχείρισης (ξενοδοχεία και διαμερίσματα), τα οποία αποτελούν τον πυρήνα της δραστηριότητας. Οι ρυθμίσεις Χρηστών, Πλάνων και Αυτοματισμών ενημερώνονται σπάνια και κυρίως από εκπαιδευμένους Experienced Managers - Platform users, και λιγότερο από τους Managers \& Owners, οι οποίοι επιζητούν μια έτοιμη λύση («out-of-the-box»).

\section{Μελλοντικές Βελτιώσεις}
\label{sec:future-work}

\subsection{Βελτιώσεις Advanced Dashboard}

Η τρέχουσα έκδοση του Advanced Dashboard απαιτεί τεχνική εξοικείωση για τη ρύθμιση παραμέτρων. Οι παρακάτω βελτιώσεις θα καταστήσουν την πλατφόρμα πιο προσιτή σε Managers χωρίς τεχνική εμπειρία, μειώνοντας την ανάγκη για υποστήριξη από Help Desk:

\begin{itemize}
    \item \textbf{GUI Builder για Template Messages:} Drag-and-drop editor για δημιουργία templates μηνυμάτων στα Auto Actions, με visual placeholders για δυναμικά δεδομένα κρατήσεων
    \item \textbf{Plans GUI:} Οπτικό interface για διαχείριση πλάνων συνδρομών με real-time preview των δυνατοτήτων
    \item \textbf{Add/Update Users GUI:} Wizard-style διαδικασία δημιουργίας και επεξεργασίας χρηστών με οπτική αναπαράσταση δικαιωμάτων
    \item \textbf{Auto Actions Visual Editor:} Flow-chart style editor με οπτικά στοιχεία για time windows, intervals, και triggers -- επιτρέποντας διαισθητική ρύθμιση χωρίς τεχνικές γνώσεις
\end{itemize}

\subsection{Επέκταση Channel Manager Support}

Η υποστήριξη επιπλέον Channel Managers θα διευρύνει τη βάση πιθανών χρηστών:

\begin{itemize}
    \item \textbf{Channex:} Δημοφιλής Channel Manager με ισχυρό API και ευρεία υιοθέτηση στην ευρωπαϊκή αγορά
    \item \textbf{Custom/Direct Integrations:} Framework για εύκολη ενσωμάτωση νέων Channel Managers μέσω standardized adapter pattern
\end{itemize}

\subsection{Analytics Page}

Σελίδα αναλυτικών στοιχείων για data-driven λήψη αποφάσεων:

\begin{itemize}
    \item \textbf{Year-over-Year Comparison:} Σύγκριση δεδομένων τρέχοντος με προηγούμενο έτος
    \item \textbf{Revenue per Property/Room:} Αναλυτικά έσοδα ανά κατάλυμα και δωμάτιο
    \item \textbf{Occupancy Rates over Time:} Ποσοστά πληρότητας με χρονική εξέλιξη
    \item \textbf{Booking Source Distribution:} Κατανομή κρατήσεων ανά πηγή (OTA, direct, κ.λπ.)
\end{itemize}

\subsection{Mobile Application}

Μετάβαση ολόκληρου του UI σε mobile εφαρμογή:

\begin{itemize}
    \item \textbf{Seamless Authentication:} Biometric login χωρίς ανάγκη επαναλαμβανόμενης σύνδεσης
    \item \textbf{Push Notifications:} Άμεσες ειδοποιήσεις για νέες κρατήσεις, μηνύματα, και κρίσιμες ενέργειες
    \item \textbf{Offline Functionality:} Πρόσβαση σε calendar και βασικές πληροφορίες χωρίς σύνδεση
    \item \textbf{Quick Actions:} Approve bookings, respond σε μηνύματα με ένα tap
\end{itemize}

\subsection{Payment Integration}
\label{subsec:payment-integration}

Ολοκληρωμένη υποστήριξη πληρωμών σε πολλαπλά επίπεδα (αυτή τη στιγμή ο Manager ή Platform User επιλέγει χειροκίνητα ότι έχει λάβει πληρωμή):

\begin{itemize}
    \item \textbf{Website Payments:} Payment gateway integration για τα auto-generated websites, επιτρέποντας άμεσες πληρωμές από guests
    \item \textbf{Manager-Platform Transactions:} Αυτοματοποιημένες πληρωμές μεταξύ Managers και πλατφόρμας για subscription fees
    \item \textbf{Owner-Manager Settlements:} Διαχείριση πληρωμών μεταξύ Owners και Managers με automatic commission calculation
\end{itemize}

\subsection{OTA Platform (Fork του Auto-Generated Website)}

Επέκταση του Auto-Generated Website framework σε πλήρες Online Travel Agency (OTA), παρόμοιο με Booking.com και Airbnb:

\begin{itemize}
    \item \textbf{Centralized Property Listing:} Όλοι οι Managers μπορούν να ανεβάσουν τα καταλύματά τους στο δικό μας OTA
    \item \textbf{Unified Search \& Booking:} Ενιαία μηχανή αναζήτησης και κράτησης για όλα τα καταλύματα της πλατφόρμας
    \item \textbf{Commission-based Model:} Έσοδα για την πλατφόρμα μέσω προμήθειας ανά κράτηση
    \item \textbf{Brand Recognition:} Δημιουργία αναγνωρίσιμου brand στην αγορά βραχυχρόνιων μισθώσεων
\end{itemize}

\section{Τεχνικά Συμπεράσματα}
\label{sec:technical-conclusions}

\textbf{Αρχιτεκτονικές αποφάσεις που δικαιώθηκαν:}

\begin{enumerate}
    \item \textbf{PayloadCMS v3:} Η επιλογή του PayloadCMS ως «Backend Framework» επέτρεψε ταχεία ανάπτυξη με type-safety. Τα collection lifecycle hooks αποδείχθηκαν ιδανικά για σύνθετη επιχειρηματική λογική.
    \item \textbf{PostgreSQL vs MongoDB:} Η επιλογή PostgreSQL δικαιώθηκε πλήρως. Οι complex queries για billing, access control, και analytics θα ήταν δυσκολότερες με document-based storage.
    \item \textbf{Serverless Architecture:} Η χρήση Vercel serverless υποδομών απλοποίησε το deployment των Auto-Generated Websites και μείωσε κάτα πολύ τα operation costs.
    \item \textbf{Monorepo Structure:} Η οργάνωση σε monorepo της κύριας πλατφόρμας διευκόλυνε τη συντήρηση και την κοινή χρήση τύπων μεταξύ frontend και backend. Επιπλέον, η πλατφόρμα, χτισμένη σε Next.js, δίνει τη δυνατότητα για \textbf{εύκολο horizontal scaling} και απλοποιημένο hosting (π.χ. σε serverless πλατφόρμες όπως Vercel, AWS Lambda), αξιοποιώντας υποδομές που επιτρέπουν γρήγορο rollout χωρίς παραδοσιακό server setup. Σημαντικό μέρος του traffic εξυπηρετείται από CDN (χάρη στο SSR/SSG), αποφορτίζοντας τον server από rendering και διανομή HTML.
\end{enumerate}

\section{Επιχειρηματικό Αντίκτυπο}
\label{sec:business-impact}

Η πλατφόρμα δημιουργεί νέες επιχειρηματικές ευκαιρίες:

\begin{itemize}
    \item \textbf{Για Managers:} Προσφέρουν premium υπηρεσίες στους Owners τους, με αυτοματοποιημένη τιμολόγηση και επαγγελματικά websites
    \item \textbf{Για Owners:} Απλές καθημερινές λειτουργίες και εξαιρετική διαχείριση προσωπικού με διαφορετικά δικαιώματα
    \item \textbf{Για Staff:} Απλοποιημένη πρόσβαση σε πληροφορίες κρατήσεων χωρίς να απαιτείται τεχνική κατάρτιση
    \item \textbf{Για Πλατφόρμα:} Εύκολη επέκταση και συντήρηση, καθιστώντας την βιώσιμη λύση για τη σύγχρονη αγορά βραχυχρόνιας μίσθωσης.
\end{itemize}
